# 게시판 3-스택 샘플 — 품질/모범사례 개선 계획

> 이 프로젝트는 **상용 품질 AI 코딩의 원천 소스**(CLAUDE.md 최우선 원칙)다. 참조 샘플([260702.004.BOARD_SAMPLE_GUIDE.md](260702.004.BOARD_SAMPLE_GUIDE.md))인 게시판 3-스택 소스를 점검해 **상용 수준으로 끌어올릴 항목**을 우선순위별로 수립한다.
>
> 대상: `samples/sample-api/.../board` (JPA/jOOQ/JDBC) · 상태: **P1 완료(커밋 709e4a1), P2·P3 대기**.
>
> **진행 현황**
> - ✅ **P1 완료**: 계층형(Controller→Service→Repository) 확립 + 좋아요/댓글형 확장 + 비즈니스 검증(좋아요 선행 댓글 422·중복제목 409·공지 403·존재 404) 3스택 + 페이징 파라미터 방어(#3) + jOOQ insert NPE 방어(#4) + 통합테스트(#1, `BoardBusinessValidationIntegrationTest`). ※ 스키마 관리(#2 Flyway)는 P3 로 이동(앱 전체 영향이라 신중 반영).
> - ✅ **P2 완료(커밋 예정)**: LIKE 와일드카드 이스케이프(3스택 `escape '\'` + `BoardRules.escapeLike`) · content `@Size(max=20000)`+길이 이식성 · 응답 DTO `tech` 제거(도메인 순수) · `updated_at` 감사(3스택) · OpenAPI `@Operation` · JPA 엔티티 id 기반 equals/hashCode. 검증: 검색 `%` 리터럴 매칭·updatedAt 갱신·size 클램프·31/31 무회귀.
> - 🔄 **P3 진행 중**: ✅ @Version 낙관적 락 완료(3스택, `BoardOptimisticLockIntegrationTest`) · ⏳ Flyway+`ddl-auto=validate`(원 #2 포함, 앱 전체) · ⏳ jOOQ codegen.

## 점검 요약

기본 계층/패턴(Controller→Service→Repository, record DTO+MapStruct+Bean Validation, ApiResponse/PageResponse/ErrorCode)은 갖춰졌다. 다만 **상용 원천 소스** 기준으로는 아래가 부족하다 — 특히 **테스트 부재·스키마 관리·입력 방어**.

## P1 — 필수(상용급 최소선)

| # | 항목 | 현재 | 개선 | 근거 |
|---|---|---|---|---|
| 1 | **회귀 테스트 부재** | board 통합/단위 테스트 0개 | 3스택 각 CRUD·페이징·검색·404·검증(400) 통합테스트(RANDOM_PORT) + 서비스 슬라이스. 참조 샘플은 **테스트가 곧 스펙** | 프로젝트 규칙: "회귀 가드 동반". 원천 소스에 테스트 없음은 치명 |
| 2 | **스키마 관리(운영급)** | `ddl-auto=create-drop`(엔티티 자동 생성) | **Flyway** `db/migration/V1__create_board_post.sql` + `ddl-auto=validate`. 데모는 스크립트로 초기 데이터(V2 seed) | 운영은 엔티티 자동 DDL 금지(가이드 DB_LAYER 2·5장). "스키마 파일 어디?" 질문의 정답을 코드로 |
| 3 | **페이징 파라미터 방어** | `size` 무제한·음수 허용 | `size` 1~100 클램프(or `@Min/@Max`), `page>=0`. 서비스에서 정규화 | 과대 `size` 자원 고갈 방지(상용 필수) |
| 4 | **jOOQ insert NPE 위험** | `returning(ID).fetchOne().get(ID)` — null 시 NPE | `fetchOptional`/null 체크 후 명확한 예외 | 방어적 프로그래밍 |

## P2 — 권장(모범사례 강화)

| # | 항목 | 현재 | 개선 |
|---|---|---|---|
| 5 | **LIKE 와일드카드 이스케이프** | 사용자 입력의 `%`/`_` 그대로 → 의도치 않은 매칭 | 검색어의 `%`,`_`,escape문자 이스케이프(3스택 공통 유틸) |
| 6 | **content 길이/이식성** | `@NotBlank`만(상한 없음) + `columnDefinition="text"`(비이식) | `@Size(max=…)` + `@Lob` 또는 명시 길이(방언 이식성) |
| 7 | **응답 DTO에 데모 라벨(`tech`) 혼입** | 도메인 `BoardPostResponse.tech` | 도메인 응답에서 분리 — 데모 표시는 응답 헤더/별도 메타 또는 스택 라벨 상수. 도메인 순수성 |
| 8 | **수정 이력(updated_at) 부재** | createdAt만 | `updated_at`(+ 필요시 created_by/updated_by). JPA 는 common-platform `BaseEntity` 감사 활용 가능 — 3스택 일관 반영 방안 결정 |
| 9 | **OpenAPI 문서화** | 엔드포인트 springdoc 애노테이션 없음 | `@Tag`/`@Operation`/`@Schema` 부여(공통 OpenAPI 이미 제공) → 자동 문서·프론트 타입생성 품질 |
| 10 | **JPA 엔티티 규약** | equals/hashCode 없음, setter 공개 | id 기반 equals/hashCode, 접근자 최소화(불변 지향) |

## P3 — 선택(운영 확장)

| # | 항목 | 내용 | 상태 |
|---|---|---|---|
| 12 | **낙관적 락(@Version)** | 동시 수정 충돌 방지(게시판 수정 시) | ✅ **완료** — 3스택 공통 `version` 컬럼 + 수정 시 `?version=` 로 낙관적 락. JPA `@Version`(jakarta)·JDBC `@Version`(spring-data)·jOOQ 는 조건부 `UPDATE ... WHERE version=?` 원자적 처리. 클라이언트 version 불일치 → 서비스가 `STALE_UPDATE`(409), flush/commit 시점 진짜 레이스 → `BoardExceptionAdvice` 가 `OptimisticLockingFailureException`→409 로 번역. 회귀 가드 `BoardOptimisticLockIntegrationTest`(3스택) + `board.html` 편집 시 version 전달·409 처리 |
| 11 | **jOOQ codegen** | 동적 API(부분 타입안전) → `jooq-codegen`(빌드타임 생성)로 완전 컴파일 타임 타입 안전성. 운영 권장(샘플은 편의상 동적, 문서 명시) | ⏳ 대기 |
| 13 | **미세 최적화** | JDBC `existsById`+`deleteById`(2쿼리) 등 정리 | ⏳ 대기 |

> **@Version 낙관적 락 설계 노트**: JPA/JDBC 는 프레임워크의 `@Version` 에 위임(수정 시 `version` 검사·증가·flush), jOOQ 는 코드젠 없는 동적 API 라 DAO 가 직접 `WHERE id=? AND version=?` + `SET version = version+1` 로 <b>원자적 조건부 갱신</b>(반영 0건이면 버전 불일치)한다. 세 방식 모두 결과적으로 동일한 계약(있으면 검사, null 이면 미검사)으로 수렴한다. JPA 는 `save()` 직후가 아니라 flush 시점에 version 이 증가하므로 응답에 증가값을 담으려면 `saveAndFlush` 가 필요하다.

## 권장 실행 순서

1. **P1 일괄**(테스트·Flyway·파라미터 방어·NPE) — 원천 소스의 신뢰성 확보. 특히 #1 테스트는 이후 리팩터링의 안전망.
2. **P2**(이스케이프·이식성·DTO 순수성·감사·OpenAPI·엔티티 규약) — 모범사례 완성도.
3. **P3**(codegen·락) — 운영 확장 시.

> 각 개선은 3스택 **동시에** 반영(원천 소스 일관성) + 회귀 가드 추가 + 이 문서/가이드 갱신 + 데모 화면 재검증(31/31 + 게시판 3종) 원칙.

# Elasticsearch Logging Strategy

> **상태(2026-07-07)**: 전략 + **공통모듈 구현·검증 완료**(ECS `dual` 기본). Phase 1(기반)·Phase 2(access/error/security/payload/method/controller)·Phase 3a(아웃바운드 HTTP)·Phase 3b(도메인 이벤트)까지 적용·회귀 검증. 적용 범위·클래스·검증은 아래 [구현 현황](#구현-현황-정본-2026-07-07-적용검증-완료) 참조. Phase 4(ES 파이프라인) **아티팩트도 작성**([`deploy/elastic/`](../deploy/elastic/README.md), 문법 검증·런타임 미검증). 남은 것은 Phase 3c(APM 연계)·실 ES 반영·Kibana — 앱 외부/플랫폼 작업.

## 목적

공통모듈을 탑재한 여러 서비스의 e2e 가시성을 Elasticsearch에서 일관되게 확보한다. 목표는 다음이다.

- 화면, 사용자, 요청, 서비스 간 호출, 예외, 보안 이벤트를 하나의 `trace.id`로 추적
- 서비스별 장애율, 지연, 보안 위배, 특정 화면 장애를 Kibana에서 바로 조회
- 공통모듈이 로깅 포맷과 필수 필드를 표준화하고, 소비 서비스는 설정만으로 참여
- 로그 파일, 수집기, Elasticsearch data stream, lifecycle 정책까지 운영 가능한 형태로 정리

## 결론

로그 포맷은 **ECS(Elastic Common Schema) 호환 JSON Lines**로 가져간다. 공통모듈 전용 필드는 `mutuus.*` namespace로 확장한다.

권장 data stream은 서비스별이 아니라 로그 종류별로 나눈다.

| 로그 종류 | `data_stream.dataset` | data stream 예 |
|---|---|---|
| 접근/요청 완료 | `mutuus.access` | `logs-mutuus.access-prod` |
| 애플리케이션 오류 | `mutuus.error` | `logs-mutuus.error-prod` |
| 보안 감사 | `mutuus.security_audit` | `logs-mutuus.security_audit-prod` |
| payload | `mutuus.payload` | `logs-mutuus.payload-prod` |
| controller entry | `mutuus.controller` | `logs-mutuus.controller-prod` |
| method args/return | `mutuus.method` | `logs-mutuus.method-prod` |
| domain event | `mutuus.domain_event` | `logs-mutuus.domain_event-prod` |
| outbound HTTP | `mutuus.http_client` | `logs-mutuus.http_client-prod` |

서비스 구분은 `service.name`으로 한다. data stream dataset에 `sample-api` 같은 서비스명을 넣지 않는다. Elastic dataset 값은 `-`를 허용하지 않으므로 서비스명을 넣으면 sanitize 규칙이 필요하고, 서비스 수만큼 data stream이 늘어난다.

## 공통 필드 표준

모든 공통모듈 로그는 아래 필드를 기본으로 가진다.

| 필드 | 타입 | 설명 |
|---|---|---|
| `@timestamp` | date | 로그 발생 시각 |
| `ecs.version` | keyword | 적용 ECS 버전 |
| `log.level` | keyword | INFO/WARN/ERROR |
| `logger.name` | keyword | Logback logger |
| `message` | text/keyword | 사람이 읽는 메시지 |
| `service.name` | keyword | Spring application name |
| `service.version` | keyword | 앱 버전. 없으면 생략 |
| `service.environment` | keyword | local/dev/stage/prod |
| `service.node.name` | keyword | `<appCode>-<instanceCode>` |
| `data_stream.type` | constant_keyword | `logs` |
| `data_stream.dataset` | constant_keyword | `mutuus.access` 등 |
| `data_stream.namespace` | constant_keyword | `local`, `dev`, `prod` 등 |
| `event.dataset` | keyword | `data_stream.dataset`과 동일 |
| `event.action` | keyword | `request.completed`, `security.authz.denied` 등 |
| `event.category` | keyword array | `web`, `authentication`, `network`, `database` 등 |
| `event.type` | keyword array | `access`, `info`, `error`, `denied` 등 |
| `event.outcome` | keyword | `success`, `failure`, `unknown` |
| `trace.id` | keyword | e2e trace id. 서비스·프로세스 경계를 넘어 유지되는 최상위 상관키 (`X-Trace-Id`, 32 hex) |
| `span.id` | keyword | 단일 호출 구간 id. **아웃바운드 호출마다 새로 발급**된다 (`X-Span-Id`, 16 hex) |
| `transaction.id` | keyword | 이 서비스가 처리한 HTTP 요청 1건의 식별자. 인바운드 요청 진입 시 1회 발급되어 요청 종료까지 불변 |
| `user.id` | keyword | 인증 완료 후 subject |
| `client.ip` | ip | 클라이언트 IP |
| `mutuus.app.code` | keyword | 4자리 앱 코드 |
| `mutuus.instance.code` | keyword | 6자리 인스턴스 코드 |
| `mutuus.screen.id` | keyword | 화면 식별자 |
| `mutuus.event.id` | keyword | 화면/도메인 이벤트 식별자 |

## 현재 필드에서 ECS로의 매핑

| 현재 | 목표 |
|---|---|
| `event` | `event.action` |
| `outcome` | `event.outcome` |
| `httpMethod` | `http.request.method` |
| `httpPath` | `url.path` |
| `httpQuery` | `url.query` |
| `httpStatus` | `http.response.status_code` |
| `durationMs` | `event.duration` nanos, legacy `mutuus.duration.ms` optional |
| `clientIp` | `client.ip` |
| `userId` / `X-User-Id` | `user.id` |
| `errorCode` | `error.code` 또는 `mutuus.error.code` |
| `exception` | `error.type` |
| `requestBody` | `http.request.body.content` |
| `responseBody` | `http.response.body.content` |
| `contentType` | `http.request.mime_type` or `http.response.mime_type` |
| `X-Trace-Id` | `trace.id` |
| `X-Span-Id` | `span.id` |
| `X-Screen-Id` | `mutuus.screen.id` |
| `X-Event-Id` | `mutuus.event.id` |
| `X-App-Code` | `mutuus.app.code` |
| `X-Instance-Id` | `mutuus.instance.code`, `service.node.name` |

초기 전환은 `dual` 모드로 한다. ECS 필드를 새로 추가하고 기존 필드는 한 릴리스 동안 유지한 뒤 제거한다.

> **매핑이 아니라 신규 필드인 항목(구현 완료)**: 위 표는 "이름만 바꾸면 되는" 것처럼 보이지만 일부는 기존 로그에 **없어 새로 채운** 필드다(모두 적용됨 — [구현 현황](#구현-현황-정본-2026-07-07-적용검증-완료) 참조).
> - `event.outcome`: `AccessLogger`/`GlobalExceptionHandler`/`SecurityAuditLogger`가 성공/실패를 판정해 신규 기록.
> - `client.ip`(access completed): `AccessLogger.requestCompleted()`에 신규 전달·기록(기존엔 수신 로그에만 있었음).
> - `event.duration`(nanos): `durationMs`(밀리초)와 별도로 나노초 필드 신규 기록(dual 기간 `durationMs` 병기).

## 공통모듈 로깅 책임 위치

| 영역 | 현재 클래스 | 책임 | 개선 방향 |
|---|---|---|---|
| Trace/MDC | `TraceFilter` | trace/span/screen/user/app/instance MDC 적재 | ECS MDC alias 추가: `trace.id`, `span.id`, `transaction.id`, `user.id`, `service.node.name`, `mutuus.*` |
| Access | `AccessLogFilter`, `AccessLogger` | 요청 수신/완료 | `request.completed`를 운영 주 로그로 표준화. `event.duration`, HTTP ECS 필드, outcome 추가 |
| Exception | `GlobalExceptionHandler` | 4xx/5xx/외부 API 오류 | `mutuus.error` dataset 또는 access 로그 내 error 필드. `error.type`, `error.code`, `error.stack_trace` |
| Security | `SecurityAuditLogger`, security handlers | 401/403/JWT/identity 위배 | `mutuus.security_audit` dataset. `event.category=authentication/iam`, `event.outcome=failure` |
| Payload | `PayloadLoggingFilter`, `Default*PayloadLogger` | request/response body | `mutuus.payload` dataset. 기본 OFF, 마스킹 필수, 길이 제한, sampling |
| Controller entry | `ControllerEntryInterceptor` | controller method 식별 | 운영 기본 OFF. `mutuus.controller` dataset |
| Method log | `ControllerMethodLoggingAspect` | args/return | 운영 기본 OFF. `mutuus.method` dataset. payload보다 더 민감하게 취급 |
| Outbound HTTP | `HttpClientLoggingInterceptor`(신규) | 하위 서비스 호출 추적 | ✅ 구현 — `http.client.completed`/`mutuus.http_client` dataset, RestClient/RestTemplate 자동 배선(기본 ON) |
| Domain event | `DomainEventLogger`/`DomainEventLoggingListener`(신규) | 발행/소비 trace 연결 | ✅ 구현 — 발행 `domain_event.published`, in-process 소비 `domain_event.consumed`/`mutuus.domain_event` dataset(기본 ON) |
| Startup audit | `SecurityConfigAuditor` 등 | 위험 설정 점검 | `mutuus.security_audit` 또는 `mutuus.config` dataset |

## 이벤트별 필드 설계

### Access completed

운영 대시보드의 중심 이벤트다. 요청마다 1건은 반드시 남긴다.

```json

  "ecs.version": "9.0.0",
  "log.level": "INFO",
  "message": "API request completed",
  "data_stream.type": "logs",
  "data_stream.dataset": "mutuus.access",
  "data_stream.namespace": "prod",
  "event.dataset": "mutuus.access",
  "event.action": "request.completed",
  "event.category": ["web"],
  "event.type": ["access"],
  "event.outcome": "success",
  "event.duration": 123000000,
  "service.name": "order-api",
  "service.environment": "prod",
  "service.node.name": "ORDR-A1B2C3",
  "trace.id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span.id": "3ff9a8981b7ccd5a",

```

### Error

5xx와 외부 API 실패는 access completed와 별개로 error 이벤트를 남긴다. stack trace는 `error.stack_trace`에 들어가게 한다.

```json
{
  "data_stream.dataset": "mutuus.error",
  "event.dataset": "mutuus.error",
  "event.action": "error.server",
  "event.category": ["web"],
  "event.type": ["error"],
  "event.outcome": "failure",
  "error.type": "java.lang.IllegalStateException",
  "error.message": "Unexpected state",
  "error.stack_trace": "...",
  "url.path": "/demo/error/server",
  "http.response.status_code": 500,
  "trace.id": "..."
}
```

### Security audit

보안 감사는 트래픽 로그와 분리한다. **요청 발신자 IP 는 dataset 에 무관하게 `client.ip` 하나로 통일**한다(access·security 혼용 금지 — 대시보드 쿼리 단순화). ECS `source.ip` 가 의미상 더 맞는 상황이 있어도, 필요 시 alias 로 두고 1차 필드는 `client.ip` 로 고정한다.

```json
{
  "data_stream.dataset": "mutuus.security_audit",
  "event.dataset": "mutuus.security_audit",
  "event.action": "security.authz.denied",
  "event.category": ["authentication", "iam"],
  "event.type": ["denied"],
  "event.outcome": "failure",
  "user.id": "alice",
  "client.ip": "10.10.1.23",
  "url.path": "/api/admin/ping",
  "rule.name": "ROLE_ADMIN required",
  "trace.id": "..."
}
```

```json
  "trace.id": "...",
  "span.id": "new-client-span"
```


## Logback/파일 정책

### 기본 원칙

- 로그 파일은 **한 줄에 JSON 객체 하나**인 JSON Lines/NDJSON로 유지한다.
- 운영 컨테이너 환경은 stdout 수집을 1순위로 둔다.
- VM/Windows 서비스/로컬 개발은 rolling file을 2순위로 둔다.
- 애플리케이션은 Elasticsearch로 직접 쓰지 않는다. Agent/Filebeat/Logstash/Vector가 수집한다.
- 애플리케이션 파일 retention은 장애 시 로컬 확인용이다. 장기 보관은 Elasticsearch lifecycle이 담당한다.

### 인코더 선택 (LogstashEncoder 유지)

현재 라이브러리는 `net.logstash.logback.encoder.LogstashEncoder`(optional)를 쓴다. ECS 전환에는 두 선택지가 있다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **LogstashEncoder 유지**(채택) | 기존 optional 의존성·include 관습 그대로. 로거별 `addKeyValue` 로 dataset·이벤트 필드를 세밀 제어(아래 dataset per-logger 참조) | ECS 필드명/타입/`ecs.version` 을 **수작업으로 맞춰야** 함 |
| `co.elastic.logging:logback-ecs-encoder`(EcsEncoder) | ECS 네이티브 출력(`ecs.version` 등 자동) | dataset 을 로그별로 다르게 싣는 라우팅 유연성이 떨어지고, 새 optional 의존성·소비자 include 관습 변경 필요 |

**결론: LogstashEncoder 를 유지한다.** 이 전략의 핵심인 "이벤트별 `data_stream.dataset` 분리"가 로거 호출부 제어를 요구하는데, 그 통제력은 LogstashEncoder + `addKeyValue` 쪽이 확실하다. ECS 규격 준수(필드명/타입)는 로거 코드와 ingest pipeline 이 함께 보장한다. 향후 dataset 라우팅을 수집기/ingest 로 완전히 이관하면 EcsEncoder 재검토 여지가 있다.

### 파일명

현재 `<appCode>-<instanceCode>.log`는 식별성이 좋지만 서비스명이 빠져 있다. 권장:

```text
logs/<service.name>/<service.name>-<appCode>-<instanceCode>.ndjson
logs/sample-api/sample-api-SMPL-ABC123.ndjson
```

호환을 고려해 파일 확장자는 `.log`를 유지해도 되지만, 문서와 수집 설정에서는 JSON Lines임을 명확히 한다.

### 롤링

권장 기본값:

| 항목 | 권장 |
|---|---|
| `maxFileSize` | 100MB |
| `maxHistory` | local/dev 7일, prod 14~30일 |
| `totalSizeCap` | local 1GB, prod 3~10GB |
| compression | Elasticsearch 수집 대상 파일은 비압축. 이미 수집 완료된 archive만 압축 |
| appender | 운영은 `AsyncAppender`로 감싸기 |

압축 파일을 수집 대상으로 삼지 않는다. 수집기는 active file과 최근 rotated file만 읽고, `.gz`는 archive로 본다.

## Elasticsearch 적재 방안

### 권장 경로

1. 애플리케이션: ECS JSON Lines를 stdout/file로 출력
2. Elastic Agent 또는 Filebeat `filestream`: JSON decode
3. Ingest pipeline: legacy 필드 보정, 필드 정규화, drop/truncate
4. Elasticsearch data stream: `logs-mutuus.<dataset>-<namespace>`
5. Kibana: service/trace/screen/security dashboard

### Filebeat/Elastic Agent parsing 핵심

수집기는 줄 단위 JSON을 decode해야 한다.

개념 예:

```yaml
filebeat.inputs:
  - type: filestream
    id: common-platform-logs
    paths:
      - D:/logs/*/*.ndjson
      - D:/logs/*/*.log
    parsers:
      - ndjson:
          target: ""
          add_error_key: true
          overwrite_keys: true
    fields_under_root: true
    fields:
      data_stream.type: logs
      data_stream.namespace: prod
```

애플리케이션 로그에 `data_stream.dataset`이 이미 들어 있으면 수집기는 그 값을 사용해 routing한다. 수집기가 auto routing을 지원하지 않는 구성이면 Logstash나 ingest pipeline에서 dataset별로 라우팅한다.

### Ingest pipeline

초기 pipeline은 다음만 수행한다.

- `@timestamp` 검증
- legacy 필드 rename
  - `X-Trace-Id` -> `trace.id`
  - `httpPath` -> `url.path`
  - `httpStatus` -> `http.response.status_code`
- `event.duration` 타입 long 보장
- `client.ip`/`source.ip` ip 타입 보장
- payload body 길이 초과 시 truncate
- 허용하지 않는 동적 header/body 필드 제거
- `data_stream.dataset` 누락 시 logger name 기반 fallback

### Mapping 정책

동적 필드 폭발을 막는다.

| 필드 | mapping |
|---|---|
| `trace.id`, `span.id`, `transaction.id` | keyword |
| `service.*`, `event.*`, `mutuus.*` | keyword 중심 |
| `event.duration` | long |
| `http.response.status_code` | integer |
| `client.ip`, `source.ip` | ip |
| `error.stack_trace`, body content | wildcard 또는 text, 검색 필요성에 따라 제한 |
| 임의 labels | flattened |
| headers | 기본 미수집. 필요 시 allowlist만 flattened |

동적 필드 폭발을 "막는다"는 방향만으로는 실효가 없다. index/component template 에 **구체 가드 값을 고정**한다.

- `index.mapping.total_fields.limit`: 기본 1000 → dataset 별 상한을 명시(access/error 는 넉넉히, payload/method 는 낮게).
- 신규 필드 자동 매핑 억제: 운영 dataset 은 `dynamic: strict` 또는 `dynamic: runtime`(즉시 색인 대신 runtime field) 로 두어 예기치 않은 필드가 매핑을 늘리지 못하게 한다.
- dotted ECS 필드(`service.name` 등)는 표준 object 확장을 쓰되, labels/headers 처럼 키가 불특정한 구역만 `flattened` 로 격리(서브필드가 매핑 수에 잡히지 않음).
- 이 값들은 소비 서비스가 아니라 **ES 측 component template** 에 둔다(앱은 로그만 뱉고, 매핑 정책은 플랫폼이 소유).

### 볼륨/샘플링 정책

retention 만으로는 비용을 못 막는다. **발생 단계 샘플링**을 dataset 특성에 맞게 둔다.

| Dataset | 샘플링 정책 |
|---|---|
| `mutuus.access` | 에러(4xx/5xx)·느린 요청은 **항상 100%**. 정상 2xx 는 고트래픽 서비스에 한해 rate 샘플링 opt-in(`trace.id` 단위로 묶어 같은 요청은 전량 유지/제외 — 부분 유실 방지). |
| `mutuus.http_client` | 신뢰 host allowlist 기반 on/off. 기본은 실패·느린 호출만. |
| `mutuus.domain_event` | publish/consume 쌍은 함께 유지(한쪽만 남기면 흐름 추적 불가). |
| `mutuus.payload`·`mutuus.method` | 운영 기본 OFF. 켜면 경로 allowlist + 길이 제한 + 낮은 rate. |

> 샘플링은 `trace.id` 경계로 일관성을 지킨다 — 같은 요청에서 파생된 로그를 반쯤 남기면 대시보드에서 "구멍 난 trace" 가 생긴다. access 를 버리는 요청은 그 요청의 error/payload 로그도 함께 버리거나, 반대로 error 가 남는 요청은 access 도 강제 유지한다.

## 구현 경계와 제약 (착수 전 필독)

전략은 옳지만, 아래 네 가지 경계를 모르고 Phase 1 을 설계하면 중간에 막힌다. 실제 소스(`TraceFilter`, `AccessLogger`, `logback-common.xml`, `IdGenerator`) 기준이다.

### 1) MDC 는 문자열 스칼라만 싣는다 — 구조 필드는 호출부/ingest 몫

`TraceFilter` 가 MDC alias 를 추가해도 MDC 는 **String 값만** 담는다. 따라서 다음은 MDC alias 로 해결되지 않는다.

| 필드 | 타입 | 채우는 위치 |
|---|---|---|
| `event.category`, `event.type` | keyword **배열** | 로거 호출부 `addKeyValue(...)` (또는 ingest) |
| `event.duration` | long | `AccessLogger` 호출부 |
| `http.response.status_code` | integer | `AccessLogger` 호출부 |
| `client.ip` / `source.ip` | ip | 호출부 문자열 → ingest 에서 ip 타입 보장 |
| `trace.id`, `span.id`, `user.id`, `service.node.name`, `mutuus.*` | keyword 스칼라 | **MDC alias 로 가능** |

즉 Phase 1 의 "TraceFilter ECS alias MDC 추가"로 커버되는 건 **스칼라 keyword 뿐**이다. 배열/숫자/ip 는 로거 코드(Phase 2)나 ingest pipeline 이 채운다.

### 2) `data_stream.dataset` 은 로거별로 싣는다 (appender customFields 로는 불가)

현재 `logback-common.xml` 의 `<customFields>` 는 **appender 단위 상수**라, access·error·security 를 한 파일/콘솔에 쓰는 구조에서 로그마다 다른 dataset 을 넣을 수 없다. 따라서:

- **주 메커니즘**: 각 로거(`AccessLogger`/`SecurityAuditLogger`/…)가 자신의 `event.dataset`(및 `data_stream.dataset`)을 `addKeyValue` 로 **직접 명시**한다.
- **보조(fallback)**: 로거가 값을 안 넣은 경우에만 ingest pipeline 이 `logger.name` 기반으로 dataset 을 보정한다.

문서 뒤쪽 "Ingest pipeline"의 `data_stream.dataset 누락 시 logger name 기반 fallback"` 은 어디까지나 보조다 — 1차 출처는 로거다.

### 3) MDC 키 노출 — 화이트리스트 제거로 해소(구현 완료)

기존 인코더는 MDC 6개만 화이트리스트(`includeMdcKeyName`)로 노출해 `X-Device-Id`/`X-App-Code`/`X-Instance-Id`/`X-Locale` 가 누락됐다. dual 기간엔 legacy + ECS alias 로 키가 배로 늘어 화이트리스트 관리가 부담이 된다. **정본은 화이트리스트를 제거**해 MDC 의 모든 키가 자동 렌더되게 한다(필터가 MDC 를 통제하므로 안전) — 신규 ECS alias(`trace.id`/`span.id`/`transaction.id`/`user.id`)와 누락됐던 `X-*` 가 모두 자동 포함된다.

### 4) `trace.id` 는 형식은 W3C 호환이나 tracer 발급값이 아니다

`IdGenerator.newTraceId()` 는 32 hex, `newSpanId()` 는 16 hex 를 생성해 **형식은 W3C(16바이트 trace / 8바이트 span) 와 호환**된다 — 예시 JSON 과 일치한다. 다만 이 값은 `TraceFilter` 가 자체 생성한 것이지 observability 패키지의 OTel tracer 가 발급한 것이 아니다.

- **이 문서의 범위 = 로그 상관(log correlation)**: 같은 `trace.id` 로 여러 로그를 묶는 것. 여기까지는 현행 그대로 달성된다.
- **Elastic APM 트레이스 연계(APM span ↔ 로그)** 는 별도 범위다. 하려면 tracer 와 `TraceFilter` 의 trace/span id **원천을 통일**해야 하며(같은 id 를 공유), 이는 Phase 3 이후의 독립 작업으로 둔다.

## Kibana Discover 활용 · 필드 노출 체크리스트

로그에 필드를 넣는다고 Discover 사이드바에 바로 뜨는 게 아니다. 아래 사슬이 이어져야 노출된다.

### 필드가 Discover 에 뜨는 조건 (사슬)

1. **앱이 값을 실제로 출력** — MDC 는 문자열 스칼라만 싣는다. `event.category`/`event.type`(배열), `event.duration`(long), `http.response.status_code`(int), `client.ip`(ip) 는 **로거 호출부 `addKeyValue` 로 넣어야** 문서에 들어가고 목록에 뜬다(MDC alias 로는 안 됨 → "구현 경계와 제약 §1").
2. **수집기가 ndjson decode + dotted 키 확장** — `service.name` 같은 점 표기가 ES 에서 `service`→`name` 객체로 펼쳐져 Discover 에 `service.name` 으로 보인다.
3. **data stream 색인 + 매핑 존재** — Discover 사이드바의 출처는 문서가 아니라 **매핑**이다. `dynamic: strict` 면 component template 에 **선등록한 ECS 필드만** 뜬다(미등록은 색인 거부 → 아예 안 보임).
4. **Data view 가 그 data stream 을 포함** — `logs-mutuus.*`(또는 dataset 별 `logs-mutuus.access-*`) data view 를 만들고 Discover 상단에서 선택해야 목록이 채워진다.

### Available vs Empty

- **Available fields**: 현재 시간범위 + KQL 결과 문서에 **값이 실린** 필드.
- **Empty fields**: 매핑엔 있으나 지금 결과에 값이 없는 필드 — 기본 OFF 인 `mutuus.payload.*`/`mutuus.method.*` 가 여기 온다(켜서 데이터가 들어오기 전까지).
- 새 필드가 안 보이면 data view **"Refresh field list"** 로 매핑 갱신분을 반영한다.

### 추천 컬럼 세트 (dataset 별)

`_source` 통짜 대신 필드를 컬럼으로 올려 표로 본다.

| Dataset | 추천 컬럼 |
|---|---|
| `mutuus.access` | `http.request.method` · `url.path` · `http.response.status_code` · `event.duration` · `event.outcome` · `user.id` · `service.name` |
| `mutuus.error` | `event.action` · `url.path` · `http.response.status_code` · `error.type` · `error.message` |
| `mutuus.security_audit` | `event.action` · `event.outcome` · `user.id` · `client.ip` · `url.path` · `rule.name` |
| `mutuus.http_client` | `http.request.method` · `url.domain` · `http.response.status_code` · `event.duration` · `event.outcome` |

### trace.id 드릴다운 순서 (장애 분석 표준 동선)

1. `logs-mutuus.*` data view 선택, 시간범위 지정.
2. 증상으로 진입 — 5xx: `http.response.status_code >= 500`, 특정 화면: `mutuus.screen.id: "ORDER_CREATE" and event.outcome: "failure"`.
3. 문제 행 펼쳐 `trace.id` 값 옆 `+` 로 필터 → 그 요청에서 파생된 **모든 dataset**(access·error·http_client·domain_event) 로그가 한 화면에 모인다.
4. `event.duration` 정렬로 병목 구간, `url.domain` 으로 하위 서비스 지연 확인.
5. 필요 시 `data_stream.namespace: "prod"` 로 환경 고정.

> 전제: 샘플링을 `trace.id` 경계로 일관 적용해야 이 동선이 "구멍 없이" 성립한다(→ "볼륨/샘플링 정책").

### 집계 · 차트(시각화)에서의 필드 사용

Discover 에 뜨는 것과 **집계 축/메트릭으로 쓸 수 있는 것**은 조건이 다르다 — 필드가 **aggregatable(doc_values 보유)** 해야 한다. Lens/TSVB/집계 기반 viz 는 필드를 **버킷(축·분할)** 또는 **메트릭(값)** 으로 쓴다. 매핑 타입이 이를 가른다.

| 필드 | 매핑 | 시각화 역할 |
|---|---|---|
| `service.name` · `event.action` · `event.outcome` · `event.category` · `mutuus.screen.id` · `url.path` · `url.domain` | keyword | Terms 버킷(막대 분할·series split·파이), 필터 |
| `@timestamp` | date | Date histogram(시계열 X축) |
| `event.duration` | long | 메트릭 — avg/max/**percentile(p95/p99)** |
| `http.response.status_code` | integer | Terms 버킷 또는 Range(2xx/4xx/5xx), count |
| `client.ip` | ip | Unique count(Cardinality), Terms(상위 IP) |
| `data_stream.dataset` · `data_stream.namespace` | constant_keyword | 필터/버킷(스트림당 단일 값) |
| `message` | text | **집계 축 불가**(검색만). 축 필요 시 `.keyword` 멀티필드 |
| `error.stack_trace` · body content | text/wildcard | 검색 전용(의도) — 집계 대상 아님 |
| labels · headers | flattened | 집계 가능하나 keyword 수준으로 제한적 |

**차원=keyword, 값=long/integer/ip/date** 로 매핑한 것이 그대로 시각화 축/메트릭이 되는 이유다. `text` 는 doc_values 가 없어 축이 못 되므로 `message`·stack_trace·body 만 text 로 두고 나머지는 keyword 로 둔다.

대표 차트(우리 dataset 그대로):
- 서비스별 장애율: Terms `service.name` + `count(status≥500)/count` (`mutuus.access`)
- p95 지연 추이: date histogram X축 + `event.duration` 95th pct, split `service.name`
- 상태코드 분포: Terms `http.response.status_code`
- 화면별 실패 Top: Terms `mutuus.screen.id`, 필터 `event.outcome: failure`
- 하위 서비스 지연: Terms `url.domain` + `event.duration` avg (`mutuus.http_client`)

> **고카디널리티 주의**: `trace.id`/`transaction.id` 는 keyword 라 집계는 되지만 **Terms 버킷으로 쪼개면 값이 요청 수만큼 폭발**한다. 이 둘은 필터·Cardinality(unique count) 로만 쓰고 축으로는 쓰지 않는다.

## 주요 의사결정

1. ECS를 표준으로 채택한다.
2. `mutuus.*` 외에는 임의 필드를 늘리지 않는다.
3. 서비스명은 `service.name`, 환경은 `data_stream.namespace`와 `service.environment`에 둔다.
4. dataset은 서비스명이 아니라 로그 종류 기준으로 둔다.
5. payload/method 로그는 운영 기본 OFF와 짧은 retention을 유지한다.
6. 애플리케이션은 Elasticsearch에 직접 쓰지 않는다.
7. 전환은 `dual` 모드로 시작해 기존 대시보드 호환성을 보호한다.
8. 로그 인코더는 `LogstashEncoder` 를 유지한다(EcsEncoder 아님) — dataset per-logger 제어력 우선.
9. `data_stream.dataset` 의 1차 출처는 **로거 호출부**이고, `logger.name` 기반 ingest 보정은 보조다.
10. 요청 발신자 IP 는 dataset 무관하게 `client.ip` 로 통일한다.
11. 이 문서의 범위는 **로그 상관(trace.id)** 까지다. Elastic APM span ↔ 로그 연계는 tracer/`TraceFilter` id 원천 통일이 선행되는 별도 작업으로 둔다.
12. 매핑 정책(총 필드 상한·dynamic 억제·flattened 격리)은 앱이 아니라 ES component template 이 소유한다.

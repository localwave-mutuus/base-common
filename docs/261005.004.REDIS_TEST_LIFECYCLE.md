# Redis 소비 시험의 생명주기와 실패 구분

2026-10-05 wave19 E / 담당 mem-pm. 대상은 샘플 시험과 소비 검증 workflow이며 운영 라이브러리 코드는 바꾸지 않는다. 0.2.6 게시 산출물을 그대로 검증하므로 0.2.7 게시가 필요하지 않다.

GitHub Actions 37313384706의 cold consumer에서 RedisCacheIntegrationTest:65가 FAIL이었다. 좁은 재현 CI 37320519322에서도 생명주기를 정리한 Cache가 FAIL, Session은 PASS였다. 두 호출의 UUID와 계산 시간이 달라 재계산된 사실은 확인했다. 가까운 시각의 Lettuce 경고를 캐시 실패 원인으로 보았던 과거 분석은 가설로 정정하고 원본 FAIL은 보존한다.

원인: Spring Data Redis 4.1.0의 기본 writer는 Lettuce처럼 ReactiveRedisConnectionFactory를 지원할 때 `put()`을 비동기로 실행한다. 기존 시험은 비동기 쓰기 완료 전 즉시 다음 조회가 HIT할 것을 가정해 경쟁했다. 실제 의존 JAR의 DefaultRedisCacheWriter 바이트코드에서 `writeAsynchronously()` → `store()` → `thenRun()` 후 Future를 기다리지 않고 반환하는 경로를 확인했다. 공식 저장소 [동일 기본 동작 이슈 #3348](https://github.com/spring-projects/spring-data-redis/issues/3348)도 이를 설명한다. 이는 Redis 복제 지연이나 로깅 변경이 아니다.

확인한 시험 구조 문제는 JUnit 관리 컨테이너의 수명과 캐시된 Spring context의 수명이 다르다는 점이다. Cache/Session의 Redis 컨테이너를 각 시험 설정의 `@Bean @ServiceConnection("redis")`으로 옮겨 Spring context가 연결과 컨테이너를 함께 소유하게 했다. Spring Boot는 컨테이너 빈을 시작하고 의존 빈이 종료된 뒤 컨테이너를 종료한다. Docker가 없을 때는 기존 `@Testcontainers(disabledWithoutDocker=true)`로 skip한다. 이는 과거 assertion 실패 원인의 확정과 구분되는 시험 안정화다.

Cache 시험은 PING, 프리픽스 설정, 정확한 Redis 키·양수 TTL·첫 반환값과 역직렬화 값의 일치, 저장 완료 후 두 번째 호출 동등성을 검증한다. 첫 compute는 한 번만 실행하고 Awaitility로 최대 5초 동안 그 첫 값의 저장만 관찰한다. 두 번째 compute도 한 번만 실행하며 반드시 같은 값을 반환해야 한다. 미저장·직렬화·캐시 미적용은 제한 시간 후 FAIL이므로 compute 재시도로 실패를 숨기지 않는다. 키는 실행별 UUID로 분리하며 wildcard KEYS에 의존하지 않는다. Spring AOP 프록시 확인만으로 캐시 advice를 단정하지 않는다.

workflow_dispatch에서 `verify_published_only=true`, `verification_scope=redis`를 선택하면 게시/전체 reactor 없이 게시된 0.2.6을 쓰는 두 변경 시험만 한 번 실행한다. `redis-cache`는 수정된 Cache만 확인하므로 이미 PASS한 Session을 반복하지 않는다. 각 XML 결과가 tests=1이며 failure/error/skip=0인지 확인해 Docker skip을 PASS로 오인하지 않는다. 기존 ecs-response 선택지는 유지한다. 최신 r3 규칙에 따라 세 번 반복이나 다른 팀 재시험은 하지 않는다.

실행 결과·최초 FAIL·실행 source SHA는 104의 `.team/state/tasks/261005-wave19-redis/checkpoint.md`와 `build/wave19-redis/`에 기록한다. 운영 캐시 동작 변경·서비스 버전 변경·DEV/PROD 배포는 이번 수정에 없다.

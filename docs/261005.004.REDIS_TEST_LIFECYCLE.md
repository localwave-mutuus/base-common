# Redis 소비 시험의 생명주기와 실패 구분

2026-10-05 wave19 E / 담당 mem-pm. 대상은 샘플 시험과 소비 검증 workflow이며 운영 라이브러리 코드는 바꾸지 않는다. 0.2.6 게시 산출물을 그대로 검증하므로 0.2.7 게시가 필요하지 않다.

GitHub Actions 37313384706의 cold consumer에서 RedisCacheIntegrationTest:65가 FAIL이었다. 두 호출의 UUID와 계산 시간이 달라 재계산된 사실은 확인했다. 가까운 시각의 Lettuce 재접속 경고는 어느 시험 컨테이너의 연결인지 입증되지 않았다. 따라서 그 경고를 캐시 실패의 확정 원인으로 삼지 않는다. 과거 FAIL은 보존하고 당시 MISS의 근본 원인은 UNPROVEN으로 남긴다.

확인한 시험 구조 문제는 JUnit 관리 컨테이너의 수명과 캐시된 Spring context의 수명이 다르다는 점이다. Cache/Session의 Redis 컨테이너를 각 시험 설정의 `@Bean @ServiceConnection("redis")`으로 옮겨 Spring context가 연결과 컨테이너를 함께 소유하게 했다. Spring Boot는 컨테이너 빈을 시작하고 의존 빈이 종료된 뒤 컨테이너를 종료한다. Docker가 없을 때는 기존 `@Testcontainers(disabledWithoutDocker=true)`로 skip한다. 이는 과거 assertion 실패 원인의 확정과 구분되는 시험 안정화다.

Cache 시험은 PING, 프리픽스 설정, 연속 두 호출의 즉시 동등성, 정확한 Redis 키·양수 TTL·첫 반환값과 역직렬화 값의 일치를 검증한다. 두 compute 사이에 Redis 진단을 끼우지 않아 기존 즉시 HIT 검증을 지연시키지 않는다. 키는 실행별 UUID로 분리하며 wildcard KEYS에 의존하지 않는다. 재시도·sleep으로 MISS를 숨기지 않는다. Spring AOP 프록시 확인만으로 캐시 advice를 단정하지 않는다.

workflow_dispatch에서 `verify_published_only=true`, `verification_scope=redis`를 선택하면 게시/전체 reactor 없이 게시된 0.2.6을 쓰는 두 변경 시험만 한 번 실행한다. 각 XML 결과가 tests=1이며 failure/error/skip=0인지 확인해 Docker skip을 PASS로 오인하지 않는다. 기존 ecs-response 선택지는 유지한다. 최신 r3 규칙에 따라 세 번 반복이나 다른 팀 재시험은 하지 않는다.

실행 결과·최초 FAIL·실행 source SHA는 104의 `.team/state/tasks/261005-wave19-redis/checkpoint.md`와 `build/wave19-redis/`에 기록한다. 운영 캐시 동작 변경·서비스 버전 변경·DEV/PROD 배포는 이번 수정에 없다.

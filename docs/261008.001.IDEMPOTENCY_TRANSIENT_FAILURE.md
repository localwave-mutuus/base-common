# 공통0.2.9 멱등 일시 실패 정책

5xx,408,429는 완료 응답으로 저장하지 않고 현재 예약을 해제한다. 같은 key의 후속 요청은 다시 owner를 호출한다. 성공 및 다른4xx는 기존처럼 응답을 재사용한다. 소비자는 재시도 가능한 응답을 확정 상태 변경 전 거절에 사용하고, 업무 command의 durable receipt/상태 precondition을 유지한다.

0.2.8에서 남은 completed transient 응답은 `IdempotencyStore.removeIfCompleted(key, expected)`의 원자 compare-and-remove 성공 후 재실행한다. 무조건 remove는 다른 retry의 새 in-progress/성공 receipt를 삭제할 수 있어 사용하지 않는다. 기본 InMemory 구현은 CAS를 제공하며 custom store는 이를 구현해야 한다. 미지원/경쟁 실패는409 `Idempotent-Replayed: transient-release-unconfirmed`로 fail-closed다. raw key/body를 로그로 출력하거나 일괄 cache/Redis cleanup하지 않는다.

처리 중 중복409,URI fingerprint mismatch409 및 실제 업무 반환 후 응답 저장의 확인 실패 보호는 유지한다. 저장소가 완료 확인 실패의 예약을 보존할 책임도 그대로다.0.2.8 게시물은 변경하지 않으며0.2.9 새 release만 소비한다.

검증: sample-api 소비자 IdempotencyTransientFailureTest 6cases, transient→동일key성공→replay/business4xx/legacy CAS/new reservation 보호/custom unsupported fail-closed/완료 확인 불명 상태 중복방어. 기존 전체 suite/실행환경/DB 시험은 반복하지 않는다. GM004 실제 DEV 원인은 MEM APP_API_BASE_URL 누락, guard 우회로 해결하지 않는다.

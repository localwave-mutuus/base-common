# 보안 하드닝 & 보안 감사 로깅 계획

> common-platform(라이브러리)의 보안 개선을 **순서대로** 반영하고, 각 보안 검사의 **위배 시 상세 보안 로그**를 남긴다.
> 검증 기준은 분리된 **보안 테스트 화면** `/demo/security.html`(+ 통합 테스트)이다.
>
> **진행 현황**: ✅ **전 Phase 완료** — Phase 0(보안 감사 로깅 기반 + 401/403 정상화) · Phase 1(신뢰경계·JWT audience·정보노출) · Phase 2(권한·전파·설정 점검) · Phase 3(CSRF 조건부·보안 응답 헤더).

## 원칙
- 기존 로깅 파이프라인(logstash JSON) 재사용, 트래픽 로그(`AccessLogger`)와 **분리된** 전용 로거 `ai.mutuus.common.security.audit`.
- optional+조건부 자동구성·토글·i18n·회귀 가드 동반(상용 품질 규약).
- **응답 ≠ 로그 분리**: 위배 상세는 로그에만, 응답은 표준 봉투(정보 최소).
- **로그 보안**: 원문 JWT/Authorization·비밀번호 미기록(주체/사유/클레임명만).

## 보안 이벤트 스키마
공통 필드: `event`, `securityEvent=true`, `outcome`(denied/blocked/rejected/suspected), `httpPath`, `clientIp`, (+MDC 자동 `X-Trace-Id`/`X-User-Id`/`appCode`/`instanceCode`), 이벤트별 필드.
심각도: 잠재 공격=WARN, 확정적 위·변조 시도=ERROR, 설정 위험(startup)=WARN.

## 이벤트 카탈로그 (검사 → 이벤트 → 레벨 → 상태)

## Phase 0 — 완료 내역 (보안 감사 로깅 기반)
- **`SecurityAuditLogger`**(`lib/.../security/audit`, 로거 `ai.mutuus.common.security.audit`) + `CommonSecurityAuditAutoConfiguration`(항상 제공, 토글 `mutuus.common.security.audit.enabled` 기본 ON) + `CommonSecurityAuditProperties`.
- **401**: `LoggingAuthenticationEntryPoint` 가 `security.authn.failed`(clientIp/reason) 기록.
- **403**: `LoggingAccessDeniedHandler`(필터 단계) + **`SecurityExceptionAdvice`**(MVC 단계, `@Order(HIGHEST_PRECEDENCE)`)가 `security.authz.denied`(principal/reason) 기록.
- **부수 버그 수정(중요)**: `@PreAuthorize` 등 **메서드 보안**이 던지는 `AuthorizationDeniedException`(=`AccessDeniedException`)이 MVC 로 전파돼 `GlobalExceptionHandler`(Exception 포괄)에 걸려 **500 + 보안 로그 누락**되던 문제를, 최고 우선순위 `SecurityExceptionAdvice` 로 잡아 **403 표준 봉투 + `security.authz.denied`** 로 바로잡음. 최상위 `exceptionHandling` 에도 로깅 핸들러를 연결해 필터 단계 인가 거부까지 로그 보장.
- **AOP 경로 의존성 제거**: 메서드 로깅 AOP 유무에 따라 예외 경로가 갈려 test=403 / live=500 로 달랐던 것을, 위 어드바이스로 **환경 무관 일관 403+로그** 로 통일.

## 검증 기준 — 보안 테스트 화면 `/demo/security.html`
- 시나리오를 유발하고 **실시간 보안 감사 로그**(전체 tail 을 `logger_name=ai.mutuus.common.security.audit` / `event=security.*` 로 필터)를 우측 패널에 표시. **Phase 0~3 시나리오 전부 활성**(401·403·스푸핑·불일치·audience·정보노출·no_authorities·전파차단·설정점검·보안헤더·CSRF).
- Phase 0 활성 시나리오: 미인증→401(`authn.failed`) · USER 토큰 ADMIN→403(`authz.denied`) · 유효 토큰 whoami→200.
- 보호 엔드포인트: `SecurityDemoController`(`/api/secure/whoami`, `/api/admin/ping` `@PreAuthorize("hasRole('ADMIN')")`) + `DemoMethodSecurityConfig`(`@EnableMethodSecurity`). ai 프로파일 mock JwtDecoder(`Bearer <name>`→주체, 권한 USER).
- 회귀 가드: `SecurityAuditLoggingIntegrationTest`(ListAppender 로 `security.authn.failed`/`security.authz.denied` 필드 검증, 유효 토큰은 위배 로그 없음). 라이브 스모크(ai 8095~8099, 기본 8095): 401/200/403 + tail 이벤트 확인.

## Phase 1 — 완료 내역 (신뢰경계·JWT audience·정보노출)
- **① X-User-Id 신뢰경계** — `mutuus.common.security.trust-forwarded-user`(기본 **false**). TraceFilter 는 인입 `X-User-Id` 를 TraceContext/MDC(→ 감사 created_by)에 싣지 않고 요청 속성으로만 보관, `AuthenticatedUserContextFilter` 가 검증 주체를 채운다. 미인증+주장 → `security.identity.header_ignored`(WARN, 폐기), 주장≠인증주체 → `security.identity.mismatch`(ERROR). 인증 주체는 항상 우선(감사 위조 방지).
- **② JWT audience/issuer** — `mutuus.common.security.audiences`/`issuer`(opt-in). `CommonJwtValidators` 가 기본(만료)+issuer+audience 검증을 조립, jwk-set-uri 존재 시 `commonJwtDecoder`(NimbusJwtDecoder)에 적용(소비자 자체 디코더 있으면 물러남). 토큰 검증 실패는 진입점이 `security.jwt.rejected`(errorCode/reason)로 분류.
- **④ 오류 응답 정보 미노출** — `mutuus.common.exception.expose-exception`(기본 **false**). 500/502/504 응답의 `error.exception`(내부 클래스명)을 제거(예외/스택은 로그에만). dev 진단 시에만 true.
- 회귀 가드: `SecurityAuditLoggingIntegrationTest`(header_ignored/mismatch/boom-무노출) · `SecurityJwtAudienceIntegrationTest`(aud 허용/거부) · `TraceFilterTest`(신뢰 게이팅) · `GlobalExceptionHandlerTest`(노출 토글). 검증 화면 `/demo/security.html` Phase 1 시나리오 활성.

## Phase 2 — 완료 내역 (권한·전파·설정 점검)
- **③ 아웃바운드 전파 allowlist** — `mutuus.common.propagation.allowed-hosts`(기본 비어=전부 전파, 하위호환). 지정 시 그 외 호스트로의 호출엔 식별 헤더(`HeaderNames.IDENTITY`: X-User-Id·X-Device-*·X-App-Code 등)를 제거하고 상관용(trace/span/locale)만 전파, `security.propagation.blocked`(targetHost/droppedHeaders) 기록. 회귀 `SecurityPropagationBlockIntegrationTest`.
- **⑧ roles 클레임 경로 + no_authorities** — `roles-claim` 중첩 경로(점, 예 `realm_access.roles`) 지원. 인증됐으나 부여 권한 0건 → `security.authz.no_authorities`(subject/rolesClaimPath). 데모 토큰 `noroles`.
- **⑤⑥ startup 설정 점검(`SecurityConfigAuditor`)** — 본문 로깅+마스킹 off → `security.config.masking_disabled`, 세션+CSRF 비활성 → `security.config.csrf_disabled_with_session`, permit-all 과대(`/**`) → `security.config.permit_all_broad`. 회귀 `SecurityConfigAuditorTest`.

## Phase 3 — 완료 내역 (CSRF 조건부·보안 응답 헤더)
- **⑥ CSRF/세션 조건부** — `mutuus.common.security.csrf-enabled`(기본 **false**, 무상태 Bearer). true 면 `CookieCsrfTokenRepository` 로 CSRF 보호 + 세션 정책 `IF_REQUIRED` — 쿠키 세션 소비 서비스가 CSRF 를 켜는 knob. (Phase 2 의 `csrf_disabled_with_session` startup 경고와 짝)
- **⑦ 보안 응답 헤더** — `mutuus.common.security.headers.*`(기본 **OFF**, HTML 서빙 시 CSP 인라인 차단 위험이라 보수적). enabled 시 Referrer-Policy·Permissions-Policy·CSP(설정 시)를 응답에 추가(Spring 기본 nosniff 유지). 회귀 `SecurityHeadersCsrfIntegrationTest`.
- 검증 화면 `/demo/security.html` Phase 3: 응답 보안 헤더 라이브 확인 + CSRF knob 안내.

## 기본값 원칙
- 행위 변경(①,③)은 안전측 기본 + opt-out, 정보노출(④)은 운영 안전 기본, 나머지(②⑥⑦)는 opt-in. 보안 감사 로깅(전 이벤트)은 기본 ON.

각 Phase 는 `/demo/security.html` 의 해당 시나리오를 "예정→동작"으로 켜고, 통합 테스트로 이벤트/필드를 검증하며 진행한다.

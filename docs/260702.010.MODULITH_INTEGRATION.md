# Spring Modulith × common-platform 통합 가이드

> **대상**: 소비 서비스를 **모듈러 모놀리스(모듈 = 바운디드 컨텍스트)** 로 구성하려는 개발자·AI. common-platform 의
> `event`(DomainEvent/EventPublisher)·`async`(TraceContext 전파)·`observability` 가 Spring Modulith 와 **어떻게 합성**
> 되는지, 무엇을 추가하면 되는지, 무엇을 점검해야 하는지 정리한다.
>
> 결론 요약: **라이브러리 변경 없이** Modulith 와 합성된다. 모듈 간 통신은 common-platform `EventPublisher`(Spring
> 이벤트 기반)를 그대로 쓰고, 신뢰성이 필요하면 `spring-modulith-events-jpa`(트랜잭셔널 아웃박스)를 추가하면 된다.
> 참조: 온보딩 [260702.009](260702.009.ONBOARDING.md) · DDD 전략 [260702.007](260702.007.PLATFORM_DDD_STRATEGY.md).

---

## 1. 왜 자연 합성인가
- common-platform `ApplicationEventPublisherAdapter` 는 Spring `ApplicationEventPublisher` 로 발행한다. Modulith 의
  `@ApplicationModuleListener`(= `@Async` + `@Transactional(REQUIRES_NEW)` + `@TransactionalEventListener`)도 **같은
  Spring 이벤트 버스**를 소비한다 → 별도 배선 없이 이벤트가 흐른다.
- 모듈 그래프는 소비자 base package 하위만 인식한다. 라이브러리(`ai.mutuus.common.*`)는 **모듈 밖 외부 의존성**이라
  경계 검증 대상이 아니다(모듈이 `ApiResponse`·`DomainEvent` 를 참조하는 것은 허용).

## 2. 의존성 (BOM 이 버전 관리)
common-platform-bom 이 `spring-modulith-bom` 을 import 하므로 **버전 없이** 추가한다.
```xml
<dependency><groupId>org.springframework.modulith</groupId>
  <artifactId>spring-modulith-starter-core</artifactId></dependency>
<!-- 신뢰성 있는 이벤트(아웃박스)가 필요하면: -->
<dependency><groupId>org.springframework.modulith</groupId>
  <artifactId>spring-modulith-starter-jpa</artifactId></dependency>   <!-- EventPublicationRegistry(JPA 아웃박스) -->
<!-- 모듈 간 호출 관측이 필요하면: -->
<dependency><groupId>org.springframework.modulith</groupId>
  <artifactId>spring-modulith-observability</artifactId></dependency>
```

## 3. 모듈 간 통신 = 이벤트 (직접 호출 금지)
모듈(바운디드 컨텍스트)은 서로의 클래스/테이블을 직접 참조하지 않는다. **common-platform 이벤트로만** 협력한다.
```java
// [order 모듈] — 발행: 트랜잭션 커밋과 함께
class PlaceOrder {
  private final EventPublisher events;
  @Transactional
  public void handle(...) {
    // ... 도메인 상태 변경 ...
    events.publish("Order.OrderPlaced", new OrderPlaced(orderId, memberId, amount)); // DomainEvent 봉투(traceId 자동)
  }
}

// [ledger 모듈] — 수신: 다른 모듈, 비동기, 새 트랜잭션
@Component
class LedgerOnOrder {
  @ApplicationModuleListener                     // 커밋 후 · 비동기 · REQUIRES_NEW
  void on(DomainEvent<OrderPlaced> e) {
    OrderPlaced p = e.payload();
    // 홀드 처리 (멱등키 = e.eventId())
  }
}
```
- `@ApplicationModuleListener` 는 **원 트랜잭션 커밋 후** 실행 → 발행 모듈의 로컬 일관성과 분리(최종 일관성).
- 멱등키는 `DomainEvent.eventId()` 사용(재시도/아웃박스 재발행 안전) — [260702.008](260702.008.VOUCHER_LEDGER_TACTICAL.md) 원장 규약과 정합.

## 4. 트랜잭셔널 아웃박스 (신뢰성) — DDD "아웃박스" 요구 충족
`spring-modulith-starter-jpa` 를 넣으면 `EventPublicationRegistry` 가 **발행 이벤트를 DB 에 기록**하고, 리스너가
완료되면 마킹한다. 애플리케이션 크래시 시 **미완료 이벤트를 재발행**한다 → 별도 브로커 없이 신뢰성 확보.
- DDD 전략문서 §7 의 "트랜잭셔널 아웃박스"를 **Modulith 가 구현**한다(라이브러리 event 코어는 봉투 규약만 제공).
- 나중에 **외부화**가 필요하면 `spring-modulith-events-kafka`/`-amqp` 로 확장 — common-platform 이 남겨둔 "브로커
  확장점"의 자연스러운 구현 경로.
- 이벤트 스토어에 저장되므로 payload(record)는 **Jackson 직렬화 가능**해야 한다(순수 record + 표준 타입 권장).

## 5. 비동기 TraceContext 전파 (반드시 점검)
`@ApplicationModuleListener` 는 `@Async` 라 **스레드 경계**를 넘는다. common-platform 의
`TraceContextTaskDecorator` 가 Boot 의 task executor 자동구성에 적용되므로, Modulith 비동기 리스너가 그 executor 를
쓰면 **traceId/userId/MDC 가 유지**된다(발행→리스너 로그 상관 보존).
- **전제**: `@Async` 활성화가 필요하면 `@EnableAsync` 를 둔다(Modulith 스타터가 필요 시 구성). 별도 커스텀 executor 를
  정의하면 그 executor 에 TaskDecorator 가 적용되는지 확인한다.
- **회귀 가드**: `Security/AsyncPropagation` 계열처럼, 발행 시 `TraceContext.put(TRACE_ID, x)` 후 리스너 스레드에서
  `TraceContext.traceId()` 가 동일값인지 확인하는 통합 테스트를 둔다(본 리포의 `ModulithEventTracePropagationIntegrationTest`).

## 6. 경계 검증 & 문서화 (Modulith 고유 이득)
```java
@Test
void 모듈경계를_검증한다() {
  ApplicationModules modules = ApplicationModules.of(MyApplication.class);
  modules.verify();                       // 모듈 간 부적절 의존(캡슐 침범) 시 실패
}
@Test
void 모듈문서를_생성한다() {
  new Documenter(ApplicationModules.of(MyApplication.class)).writeDocumentation(); // PlantUML/Asciidoc
}
```
- 각 모듈의 **공개 API 는 최상위 패키지**에, 내부는 하위 패키지(`internal`)에 둬 캡슐화한다.
- 다른 모듈이 필요로 하는 것은 **이벤트 + 공개 인터페이스(포트)** 로만 노출(전략문서 §9 헥사고날과 정합).

## 7. 관측(observability)
`spring-modulith-observability` 는 **모듈 간 호출에 span/metric** 을 추가한다. common-platform 의 HTTP e2e 추적
(`TraceFilter`, `service.name` 태그)과 **계층이 달라 상보적**이다(중복 아님). 스팬 증가(비용)만 고려.

## 8. MSA 로의 진화 (전략문서 §8 로드맵)
- 모듈 경계를 처음부터 강하게(이벤트/포트만) 그으면, 트래픽/조직 성장 시 **모듈을 서비스로 추출**하는 것이
  리팩터링이 아니라 "이동"이 된다.
- 이벤트 계약(`type`/payload)을 그대로 유지하고, in-process 전달을 `-events-kafka/amqp` 외부화로 바꾸면 서비스 분리.

## 9. 체크리스트 (Modulith 도입)
- [ ] `spring-modulith-starter-core`(+ 필요 시 `-jpa`/`observability`) 추가(버전 없음 — BOM).
- [ ] 모듈 = base package 직속 하위 패키지 = 바운디드 컨텍스트. 내부는 `internal` 로 캡슐화.
- [ ] 모듈 간 통신은 **`EventPublisher` 이벤트 + 공개 포트**만(타 모듈 클래스/테이블 직접 참조 금지).
- [ ] `@ApplicationModuleListener` 수신 멱등(`DomainEvent.eventId()`).
- [ ] `ApplicationModules.verify()` 테스트 통과.
- [ ] 비동기 TraceContext 전파 회귀 테스트.
- [ ] (신뢰성) 아웃박스(`-jpa`) + payload 직렬화 가능.

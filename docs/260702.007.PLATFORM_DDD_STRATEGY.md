## 0. 확정 필요 가정 (개발 착수 전 합의)
설계를 근본적으로 가르는 항목이다. AI 는 구현 중 이 값에 의존하는 코드를 만들 때 **가정을 주석으로 명시**한다.

- `[가정 A]` **쌍방발행 = 상호 채권/채무(외상)** 인가, 각자 독립 발행인가 → 장부(후불) 컨텍스트 존재 여부.
- `[가정 B]` **배달 = 물리 물류(라이더/기사)** 인가 **디지털 이행** 인가 → `delivery` 분리/구현 방식.
- `[가정 C]` **바우처 = 선불 증표**, **장부거래 = 후불 상호계정 + 월말 순액정산(오프라인)** → 두 패러다임 분리(§4).
- `[가정 D]` 세금계산서·오프라인 결제(현금/카드)는 **플랫폼 외부** — 우리는 "지시/명세/증빙연동"만 소유.
- `[가정 E]` 인증은 **별도 인증 MSA에 위임**(common-platform 모델). 회원 컨텍스트는 프로파일/역할만.

## 1. 비전 & 도메인 한 줄 정의
> 두 주체가 **바우처를 쌍방 발행·교환**하고, **바우처로 서비스를 주문·이행(배달 포함)** 하며, 상호거래는 **월 단위로
> 누적 후 월말에 순액만 오프라인 정산(세금계산서 발행)** 하는 **가치교환 플랫폼**. 여기에 **광고·이벤트·후원·고객지원**
> 이 부가된다.

두 개의 가치이동 축이 공존한다(§4):
1. **바우처(선불 토큰)**: 발행 → 보유/교환 → 상환(서비스 주문).
2. **장부거래(후불 상호계정)**: 월중 상호 차변/대변 누적 → 월마감 → 순액 확정/합의 → 세금계산서 → 오프라인 수납.

## 2. 유비쿼터스 언어 (Ubiquitous Language) — **네이밍 단일 출처**
AI 는 코드·API·이벤트·테이블에서 **아래 영문 식별자만** 사용한다(임의 동의어 금지). 한국어는 문서·주석·i18n 메시지에.

| 한국어 | 정의 | 코드 식별자(영문) | 소속 컨텍스트 |
|---|---|---|---|
| 바우처 | 발행된 가치 증표(선불) | `Voucher` | voucher |
| 발행 | 바우처를 생성·부여 | `issue` / `VoucherIssued` | voucher |
| 상환 | 바우처를 서비스/가치로 소진 | `redeem` / `VoucherRedeemed` | voucher |
| 소유이전 | 바우처 소유자 변경 | `transfer` / `VoucherTransferred` | voucher |
| 쌍방발행 | 양 주체가 서로에게 발행 | `bilateralIssuance` | voucher / settlement |
| 교환 | 바우처↔바우처 거래 | `Exchange` / `Trade` | exchange |
| 오퍼 | 교환 제안 | `Offer` | exchange |
| 원장 | 바우처 잔액 이중기입 장부(선불) | `Ledger` / `Account` / `Entry` | ledger |
| 홀드 | 결제 확정 전 잔액 예약 | `hold` / `FundsHeld` | ledger |
| 차감 | 확정 차변 | `debit` / `FundsDebited` | ledger |
| 환급 | 홀드/차감 되돌림 | `refund` / `FundsRefunded` | ledger |
| 장부거래 | 후불 상호계정 거래(월정산) | `Settlement` / `TradeAccount` | settlement |
| 상호거래 | 상호계정의 개별 차·대변 | `MutualCharge` | settlement |
| 월마감 | 정산 주기 마감 | `closePeriod` / `PeriodClosed` | settlement |
| 순액 | 월말 상계 후 잔액 | `NetAmount` / `NetSettlement` | settlement |
| 양자합의 | 순액을 양측이 확정 | `reconcile` / `SettlementConfirmed` | settlement |
| 세금계산서 | 전자세금계산서 | `TaxInvoice` | tax |
| 서비스카탈로그 | 교환대상 서비스·가격 | `Catalog` / `ServiceItem` | catalog |
| 주문 | 바우처→서비스 주문 | `Order` | order |
| 이행/배달 | 주문 서비스의 이행 | `Delivery` / `Fulfillment` | delivery |
| 후원 | 수혜자 대상 쿠폰 발행 | `Sponsorship` | sponsorship |
| 수혜자 | 후원 대상(지자체/기관) | `Beneficiary` | sponsorship / membership |
| 쿠폰 | 후원으로 발행된 특수 바우처 | `Coupon`(=제약 있는 `Voucher`) | sponsorship→voucher |
| 기부금영수증 | 후원 증빙 | `DonationReceipt` | tax |
| 광고 | 노출/클릭 지면 | `Ad` / `AdPlacement` | advertising |
| 캠페인/이벤트 | 프로모션·보상 | `Campaign` | event |
| 보상 | 캠페인 지급 | `Reward` | event→voucher/ledger |
| 회원 | 주체(개인/파트너/기관) | `Member` / `Party` | membership |
| 고객지원 | 문의·분쟁·티켓 | `SupportTicket` | customer-support |

> 규칙: **애그리거트=명사 단수 PascalCase**, **도메인이벤트=과거분사**(`VoucherIssued`), **유스케이스=명령 동사**(`PlaceOrder`).

## 3. 서브도메인 분류 (투자·build/buy)
| 유형 | 서브도메인 | 판단 |
|---|---|---|
| **Core**(자체개발·최고인재) | voucher, exchange, **settlement(장부거래)**, order·delivery | 플랫폼 차별화. 특히 settlement 의 월말 netting 이 독창성 |
| **Supporting**(자체개발·표준) | catalog, advertising, event(campaign), sponsorship, customer-support | 필수지만 경쟁우위 아님 → 검증된 패턴 |

## 4. 두 가치 패러다임 (반드시 분리) `[결정]`
| 축 | 바우처(voucher/ledger) | 장부거래(settlement) |
|---|---|---|
| 성격 | **선불 토큰** | **후불 상호외상** |
| 시점 | 발행 즉시 가치 | 월중 누적, 월말 확정 |
| 정산 | 온라인(원장 이체) | **오프라인 순액**(플랫폼 외부) |
| 세무 | 상환 시 매출 | 월 순액 기준 **세금계산서** |
| 불변식 | 이중지불 금지 | 순액 = Σ차변 − Σ대변, 양자합의 |

→ 하나의 "결제/원장"으로 합치지 말 것. 서로 다른 경계 컨텍스트.

## 5. 경계 컨텍스트 카탈로그
각 항목: **책임 · 핵심 애그리거트 · 불변식 · 소유데이터 · 발행이벤트(OHS/PL) · 소비이벤트 · 외부연동**.

### 5.1 voucher (Core)
- 책임: 바우처 수명주기(발행·보유·소유이전·상환·만료·회수).
- 애그리거트: `Voucher`(id, owner, faceValue, constraints, status).
- 상태: `ISSUED → ACTIVE → (TRANSFERRED)* → REDEEMED | EXPIRED | REVOKED`.
- 불변식: 상환/이전은 `ACTIVE` 에서만; 소유이전은 잔액 무결성 유지.
- 발행이벤트: `VoucherIssued/Transferred/Redeemed/Expired/Revoked`.
- 소비: `Exchange.ExchangeMatched`, `Sponsorship.CouponRequested`, `Campaign.RewardGranted`, `Order.RedeemRequested`.

### 5.2 ledger (Core) — 선불 잔액
- 책임: 바우처 가치의 **이중기입** 잔액/이체(hold·debit·credit·refund).
- 애그리거트: `Account`, `Entry`(불변 원장 라인).
- 불변식: Σ debit = Σ credit(이중기입); 홀드≤가용잔액; 멱등 이체.
- 발행: `FundsHeld/Debited/Credited/Refunded`.
- 소비: `Order.OrderPlaced`(홀드), `Order.OrderPaid`(차감), `Delivery.DeliveryFailed`(환급).

### 5.3 settlement (Core) — 후불 장부거래
- 책임: 양자 상호계정, 월 사이클, 순액 정산, 세금계산서 트리거.
- 애그리거트: `TradeAccount`(양자쌍), `Period`(월), `MutualCharge`, `Statement`, `NetSettlement`.
- 상태: `OPEN → CLOSING → CONFIRMED(양자합의) → INVOICED → SETTLED(오프라인 수납확인)`.
- 불변식: `net = Σ(A→B) − Σ(B→A)`; 마감 후 해당 Period 에 신규 charge 불가; **양측 confirm** 없이는 INVOICED 금지.
- 발행: `PeriodClosed/SettlementConfirmed/TaxInvoiceRequested/SettlementSettled`.
- 외부: 세금계산서(tax 컨텍스트 경유), 오프라인 수납(수동 확인/외부 결제 시스템 → 우리는 `markSettled`).

### 5.4 exchange (Core)
- 책임: 바우처↔바우처 오퍼 등록·매칭·거래 실행.
- 애그리거트: `Offer`, `Trade`. 발행: `OfferPlaced/ExchangeMatched/ExchangeCancelled`. 소비: voucher/ledger 결과.

### 5.5 catalog (Supporting)
- 책임: 교환대상 서비스·바우처 가격·가용/재고. 애그리거트: `ServiceItem`. 발행: `ServiceItemPublished/PriceChanged`.

### 5.6 order (Core)
- 책임: 바우처→서비스 주문·결제(원장 홀드/차감)·주문 사가 오케스트레이션.
- 애그리거트: `Order`(lines, amount, status). 상태: `CREATED → PAID → FULFILLING → COMPLETED | CANCELLED`.
- 발행: `OrderPlaced/OrderPaid/OrderCancelled/OrderCompleted`. 소비: `FundsHeld/Debited`, `Delivery.Delivered/Failed`.

### 5.7 delivery (Core) `[가정 B]`
- 책임: 이행/배달 배정·상태. 애그리거트: `Delivery`. 상태: `REQUESTED → ASSIGNED → IN_TRANSIT → DELIVERED | FAILED`.
- 발행: `DeliveryAssigned/Delivered/Failed`. 소비: `Order.OrderPaid`(이행요청).

### 5.8 sponsorship (Supporting)
- 책임: 후원자→수혜자(지자체/기관) 쿠폰 발행·정책·기부영수증.
- 애그리거트: `Sponsorship`, `Beneficiary`(참조). 발행: `SponsorshipCreated/CouponRequested/DonationReceiptRequested`.
- 관계: voucher 에 **발행 명령**(제약 쿠폰), tax 에 **기부영수증 요청**.

### 5.9 event(campaign) (Supporting)
- 책임: 프로모션·보상 규칙·지급. 애그리거트: `Campaign`, `Reward`. 발행: `CampaignStarted/RewardGranted`.
- 관계: 보상 지급을 voucher.issue / ledger.credit 로 사가.

### 5.10 advertising (Supporting)
- 책임: 지면·타게팅·노출/클릭 집계. 애그리거트: `AdPlacement`, `Impression`. 소비: membership(타게팅), catalog.

### 5.11 customer-support (Supporting)
- 책임: 티켓/분쟁/상담. 소유: `SupportTicket` 뿐. 다른 컨텍스트는 **읽기모델(CQRS)** + 환불/조정 **명령(ACL)**.

### 5.12 membership (Generic)
- 책임: 회원/파트너/기관 프로파일·역할·수혜자. auth MSA 를 ACL 로 흡수. 발행: `MemberRegistered/MemberRoleChanged`.

### 5.13 tax (Generic, 외부 ACL)
- 책임: 전자세금계산서·기부금영수증을 **외부 사업자(예: 국세청/팝빌) 규격에 Conformist** 로 발급. 애그리거트: `TaxInvoice`, `DonationReceipt`. 어댑터만, 도메인 로직 최소.

### 5.14 notification (Generic)
- 책임: 전 컨텍스트 이벤트 구독 → 채널 발송. 읽기전용 구독자.

## 6. 컨텍스트 맵 (관계 + DDD 패턴)
표기: **PL**=Published Language, **OHS**=Open Host Service, **ACL**=Anti-Corruption Layer, **CF**=Conformist,
**P**=Partnership, **C/S**=Customer/Supplier(U=Upstream, D=Downstream).

```
[auth MSA] ──ACL──▶ membership ──U(소유/타게팅)──▶ (advertising, event, sponsorship, order)
event(campaign) ──reward 사가──▶ voucher(OHS/PL) ◀── CouponRequested ── sponsorship
                                    │                         │ DonationReceiptRequested
       exchange ──ExchangeMatched──▶│                         ▼
                                    ▼                       tax ──ACL/CF──▶ [국세청/전자세금계산서]
       order ──saga(U)──▶ ledger(OHS/PL) ◀── charge/net ── settlement ──TaxInvoiceRequested──▶ tax
         │ OrderPaid                                     (Partnership: 양자합의)
         ▼                                                     │ NetSettlement(순액)
       delivery ──Delivered/Failed──▶ order                    ▼ 오프라인 수납(플랫폼 외부)
customer-support ──읽기모델(D)+환불/조정 명령(ACL)──▶ order/delivery/ledger/settlement
notification ── 전 컨텍스트 이벤트 구독(D)
```
- **Partnership**: settlement 양자합의(대칭적 협의) — C/S 아님.
- **ACL**: tax↔외부 세무, membership↔auth, customer-support↔타 컨텍스트.
- **OHS+PL**: voucher/ledger 는 이벤트로 공개 계약 제공(하위가 소비).

## 7. 통합 & 일관성 전략 `[결정]`
- **경계 내부** = 강한 일관성(단일 애그리거트/로컬 트랜잭션). **경계 간** = 최종 일관성(**이벤트 + 사가**).
- **사가(오케스트레이션)**: 주문 결제·이행처럼 다단계+보상 필요한 흐름은 **오케스트레이션 사가**(order 가 조정자). 단순 통지는 코레오그래피.
- **트랜잭셔널 아웃박스**: 이벤트 발행은 로컬 트랜잭션과 원자적으로(outbox). common-platform `EventPublisher`/`DomainEvent` 를 브로커 어댑터로 확장.
- **멱등성**: 모든 상태변경 커맨드/이벤트 소비는 `Idempotency-Key`/이벤트 dedup(common-platform 멱등성). 이중지불·중복정산 방지의 1차 방어선.
- **추적**: `X-Trace-Id`/`userId` 자동 전파(common-platform)로 발행→주문→배달→정산 체인 상관.

### 대표 사가 — 바우처 주문(배달 케이스)
```
order.PlaceOrder
 └▶ ledger.Hold(홀드)                → FundsHeld
     └▶ order.MarkPaid → ledger.Debit → FundsDebited
         └▶ delivery.RequestFulfillment → Delivered
             └▶ order.Complete
보상: Delivery.Failed | 취소 → ledger.Refund → order.Cancel
```

### 도메인 이벤트 계약 규약 (common-platform `DomainEvent<T>`)
- `type` = `"<Context>.<Aggregate><PastVerb>"` 예 `"Voucher.VoucherIssued"`, `"Settlement.PeriodClosed"`.
- 봉투 필수: `eventId`, `type`, `occurredAt`, `traceId`, `userId`, `payload`(불변 record).
- **호환성**: payload 는 하위호환(필드 추가만), 삭제/의미변경은 새 `type` 버전(`.v2`). 소비자는 미지 필드 무시.

## 8. 배포 단위 & 조직 정렬 (Conway) `[결정]`
경계 컨텍스트 ≠ 즉시 서비스. **Spring Modulith 모듈러 모놀리스로 경계를 코드로 확정 → 점진 추출**.

| 그룹(팀) | 초기 배포단위 | 이후 분리 |
|---|---|---|
| 가치·정산 | `value`(voucher+ledger), `settlement`, `tax`(어댑터) | voucher↔ledger 분리 |
| 거래 | `commerce`(order+delivery+catalog), `exchange` | order↔delivery 분리 |
| 성장·지원 | `growth`(advertising+event+sponsorship), `customer-support` | 각각 분리 |
| 범용 | `membership`(+auth 위임), `notification` | — |

- 초기 ~6 배포단위 → 트래픽/조직 성장 시 **모듈을 서비스로 추출**(리팩터링 아님).
- 경계를 처음부터 **패키지/모듈로 강하게** 그어야 추출이 쉽다(모듈 간 직접 호출 금지, 이벤트/포트만).

## 9. 아키텍처 표준 (모든 서비스 공통) `[결정]`
- **헥사고날(포트-어댑터) + DDD 계층**. 의존 방향은 항상 안쪽(domain)으로.
```
<service>/ai/mutuus/<context>
 ├─ interfaces/   rest(Controller·DTO record) · event(consumer)      # 인바운드 어댑터
 ├─ application/  UseCase(트랜잭션 경계) · Saga · port/(아웃바운드 포트)
 ├─ domain/       Aggregate · VO · DomainEvent · Repository(인터페이스)  # 프레임워크 무의존
 ├─ infrastructure/ persistence(JPA/jOOQ·Mapper) · client(ACL) · messaging(outbox)
 └─ config/
```
- **domain 순수성**: domain 패키지는 Spring/JPA/브로커를 import 하지 않는다(POJO/record + 포트 인터페이스).
- **영속기술**: 서비스별 **하나만** 선택(예: 커머스=JPA, ledger/settlement=jOOQ/JDBC 명시 SQL·정합성). 샘플의 `board/{jpa,jooq,jdbc}` 혼재 구조는 **기술 비교용**이므로 실서비스에 복제 금지.
- **common-platform 소비**: `starter-web` + `common-platform-bom` 1줄. 표준 응답 `ApiResponse`/`PageResponse`, 에러 `ErrorCode`+`BusinessException`, 이벤트 `DomainEvent`/`EventPublisher`, 멱등 `Idempotency-Key`, 인증 위임(Bearer), 보안 하드닝([260702.006](260702.006.SECURITY_HARDENING.md)).
- **외부 연동(세무·오프라인결제·auth)** 은 각 컨텍스트의 **ACL 어댑터**로 격리 — 라이브러리·domain 에 넣지 않는다.
- CRUD 관용구는 게시판 3-스택 가이드([260702.004](260702.004.BOARD_SAMPLE_GUIDE.md))의 계층/DTO/MapStruct/검증 규약을 따른다(단, 패키지는 위 헥사고날 구조).

## 10. 컨텍스트별 착수 우선순위 (로드맵)
1. **membership(위임) + voucher + ledger** — 가치 코어(선불). 발행/보유/상환 + 원장. → 전술설계 [260702.008](260702.008.VOUCHER_LEDGER_TACTICAL.md).
2. **catalog + order + delivery** — 서비스교환(주문·배달) + 주문 사가.
3. **settlement + tax** — 장부거래(후불) 월정산 + 세금계산서. `[가정 A/C/D]` 확정 후.
4. **exchange** — 바우처 교환.
5. **event + sponsorship + advertising** — 성장.
6. **customer-support + notification** — 운영.

## 11. AI 완료기준(DoD) — 각 컨텍스트 구현 시 필수
- [ ] 유비쿼터스 언어(§2) 식별자만 사용(동의어·임의 약어 금지).
- [ ] domain 패키지 프레임워크 무의존(순수 애그리거트/VO/이벤트/포트).
- [ ] 애그리거트 불변식(§5)을 **도메인 계층에서** 강제(서비스/컨트롤러가 아니라).
- [ ] 상태전이는 명시 상태기계로(불법 전이 예외 = `BusinessException`+도메인 `ErrorCode`).
- [ ] 경계 간 통신은 **이벤트/포트만**(다른 컨텍스트 테이블·클래스 직접 참조 금지).
- [ ] 상태변경 커맨드/이벤트 소비 **멱등** 보장.
- [ ] 도메인 이벤트 `type`/payload 규약(§7) 준수 + 하위호환.
- [ ] 외부연동은 ACL 어댑터 뒤로(도메인 오염 금지).
- [ ] 표준 응답/에러/페이징(common-platform) + i18n 메시지 키.
- [ ] 회귀 테스트(유스케이스·사가·불변식) + 한국어 문서(설계 근거·AI 변경관리 지침) 동반.
- [ ] `[가정]` 에 의존하는 코드는 가정을 주석으로 명시.

## 12. 부록 — 도메인 이벤트 지도(요약)
| 발행 컨텍스트 | 이벤트 `type` | 주 소비자 |
|---|---|---|
| voucher | `Voucher.VoucherIssued/Transferred/Redeemed` | ledger, notification, settlement |
| ledger | `Ledger.FundsHeld/Debited/Credited/Refunded` | order, notification |
| order | `Order.OrderPlaced/Paid/Cancelled/Completed` | ledger, delivery, customer-support |
| delivery | `Delivery.DeliveryAssigned/Delivered/Failed` | order, notification |
| exchange | `Exchange.OfferPlaced/ExchangeMatched` | voucher, ledger |
| settlement | `Settlement.PeriodClosed/SettlementConfirmed/TaxInvoiceRequested/Settled` | tax, notification |
| sponsorship | `Sponsorship.CouponRequested/DonationReceiptRequested` | voucher, tax |
| event | `Campaign.CampaignStarted/RewardGranted` | voucher, ledger |
| membership | `Membership.MemberRegistered/RoleChanged` | 다수(타게팅/권한) |

> 이 지도는 계약의 출발점이다. 새 이벤트/소비 추가 시 **이 표와 §2 용어집을 먼저 갱신**한 뒤 코드에 반영한다(문서-코드 동기화).

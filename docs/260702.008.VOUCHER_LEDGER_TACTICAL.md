# 전술설계 — voucher · ledger (가치 코어) (AI 구현 지침)

> **범위**: 전략설계 [260702.007](260702.007.PLATFORM_DDD_STRATEGY.md) 로드맵 1순위 **가치 코어(선불)** — `voucher`(바우처
> 수명주기) + `ledger`(잔액 이중기입). 이벤트 스토밍 결과(애그리거트·명령·이벤트·정책·불변식·읽기모델)와 상태기계·
> 영속·동시성·API·테스트를 확정한다. 전략문서의 §2 유비쿼터스 언어·§9 아키텍처 표준·§11 DoD 를 전제로 한다.
> 표기: `[가정]`=사업 확인 필요, `[결정]`=확정 지침.

## 0. 핵심 설계 결정 — voucher ↔ ledger 관계
`[결정]` **Voucher = 개별 증표(전이·교환 가능한 단위), Ledger = 회원의 지불가능 잔액 집계(주문 결제용).** 두 개념을
분리하되 **잔액은 원장이 진실의 원천**이다(바우처 상태 합산이 아니라 원장 이체가 잔액을 결정 — 이중지불·감사 무결성).

- 발행: `VoucherIssued` → ledger 가 수취인 계정에 **credit**(가용잔액 증가).
- 상환(주문결제): order 사가가 ledger 에 **hold→debit**. 상환 완료 시 voucher 는 `REDEEMED` 로 마킹(추적용).
- `[가정]` 바우처 1장 = 특정 금액(faceValue) 단위인지, 부분상환 허용인지. 기본 가정: **부분상환 허용**(원장 금액 기준),
  바우처는 발행/전이/만료의 "증표"로서 상태를 가지되 지불은 원장 잔액에서 이뤄진다.

## 1. voucher 컨텍스트

### 1.1 이벤트 스토밍
- **Commands** → **Domain Events**
  - `IssueVoucher` → `VoucherIssued`
  - `TransferVoucher` → `VoucherTransferred`
  - `RedeemVoucher` → `VoucherRedeemed`
  - `ExpireVoucher`(스케줄) → `VoucherExpired`
  - `RevokeVoucher`(관리/후원회수) → `VoucherRevoked`
- **Policies(정책/반응)**
  - `VoucherIssued` ⇒ ledger 에 `CreditFunds`(수취인 계정 가용잔액 +faceValue).
  - `VoucherExpired`/`VoucherRevoked` ⇒ ledger 에 `DebitOrReverse`(미사용 잔액 회수) — `[가정]` 만료 시 잔액 소멸 정책.
  - `Sponsorship.CouponRequested` ⇒ 제약(용도·기간·수혜자) 포함 `IssueVoucher`.
  - `Exchange.ExchangeMatched` ⇒ `TransferVoucher`(소유이전).
- **Read Models**: `VoucherView`(소유자별 목록/상태/만료임박), `IssuanceHistory`.

### 1.2 애그리거트 `Voucher`
```
Voucher (aggregate root)
  id: VoucherId (ULID)
  issuerId: MemberId          // 발행 주체(쌍방발행: 어느 쪽이든)
  ownerId: MemberId           // 현재 소유자
  faceValue: Money            // VO(amount, currency)
  kind: VoucherKind           // NORMAL | COUPON(후원)
  constraints: Constraints    // VO: expiresAt, usableScope, beneficiaryOnly...
  status: VoucherStatus
  version: long               // 낙관적 락(@Version)
```
- **불변식(도메인 계층 강제)**:
  1. `transfer`/`redeem` 은 `ACTIVE` 에서만.
  2. `COUPON` 은 `constraints.usableScope`·수혜자 제한을 위반하는 상환 불가.
  3. 만료(`expiresAt` 경과)면 어떤 상태변경도 `EXPIRED` 전이 외 불가.
  4. `faceValue.amount > 0`, currency 일치.

### 1.3 상태기계
```
ISSUED ──activate──▶ ACTIVE ──transfer──▶ ACTIVE(ownerId 변경)
                        │──redeem──▶ REDEEMED
                        │──expire──▶ EXPIRED
                        │──revoke──▶ REVOKED
(불법 전이: BusinessException + VoucherErrorCode.ILLEGAL_TRANSITION)
```
> `ISSUED→ACTIVE` 는 발행 즉시 자동(별도 활성화 단계가 없으면 생략, 발행=ACTIVE 로 시작 가능 — `[가정]`).

## 2. ledger 컨텍스트 (이중기입)

### 2.1 이벤트 스토밍
- **Commands** → **Events**
  - `OpenAccount` → `AccountOpened`
  - `CreditFunds(opId, accountId, amount, ref)` → `FundsCredited`
  - `HoldFunds(opId, accountId, amount, ref)` → `FundsHeld` | `HoldRejected`(잔액부족)
  - `DebitFunds(opId, holdId)` → `FundsDebited`
  - `RefundFunds(opId, ref)` → `FundsRefunded`
- **Policies**: `Order.OrderPlaced` ⇒ `HoldFunds`; `Order.OrderPaid` ⇒ `DebitFunds`; `Delivery.DeliveryFailed`/취소 ⇒ `RefundFunds`.
- **Read Models**: `BalanceView`(available = posted − held), `LedgerStatement`.

### 2.2 애그리거트 — `Account` + 불변 `Entry`
```
Account (aggregate root)
  id: AccountId
  memberId: MemberId
  balancePosted: Money    // 확정 잔액
  balanceHeld: Money      // 홀드 합계
  version: long
  // available = balancePosted - balanceHeld

Entry (불변 원장 라인; Account 애그리거트 내부 또는 별 애그리거트 [결정: 같은 트랜잭션])
  id, accountId, type(CREDIT|HOLD|DEBIT|REFUND|RELEASE), amount, opId(멱등키), ref(voucherId/orderId), createdAt
```
- **불변식**:
  1. **이중기입**: 모든 이동은 균형(합계 0) — 대응 Entry 쌍 또는 계정간 이체는 (출금−, 입금+) 동시.
  2. `HOLD` 는 `available ≥ amount` 일 때만(음수 금지).
  3. `DEBIT` 는 대응 `HOLD` 존재 시에만(홀드 없는 확정차감 금지).
  4. **멱등**: 같은 `opId` 재적용은 무효과(재시도 안전) — 이중지불 1차 방어.
- **동시성**: 계정 단위 낙관적 락(`@Version`) + `opId` 유니크 인덱스. 충돌 시 재시도/`STALE` 반환(게시판 낙관락 패턴 재사용).

## 3. voucher ↔ ledger 통합 (사가/이벤트)
```
IssueVoucher(voucher) ──tx──▶ VoucherIssued(outbox)
        └▶ [policy] ledger.CreditFunds(opId=eventId, ownerId, faceValue, ref=voucherId)
                          └▶ FundsCredited (가용잔액 +)
주문결제(요약, 상세는 order 전술문서):
  order.OrderPlaced ─▶ ledger.HoldFunds ─▶ FundsHeld ─▶ order.MarkPaid ─▶ ledger.DebitFunds ─▶ FundsDebited
                                                                     └▶ voucher.RedeemVoucher(추적)
  실패/취소 ─▶ ledger.RefundFunds(보상)
```
- **원자성**: 각 서비스 내부는 로컬 트랜잭션 + **트랜잭셔널 아웃박스**로 이벤트 발행. 소비는 멱등(`opId=eventId`).
- **일관성 경계**: voucher 상태와 ledger 잔액은 **최종 일관**(짧은 지연 허용). 사용자 가용잔액의 진실은 ledger.

## 4. API 스케치 (common-platform 표준 봉투)
얇은 컨트롤러 → application UseCase(tx) → domain. 응답 `ApiResponse`, 목록 `PageResponse`, 오류 `ErrorCode`+`BusinessException`.
모든 상태변경은 `Idempotency-Key` 헤더 필수.

| 메서드/경로 | 유스케이스 | 실패 |
|---|---|---|
| `POST /vouchers` | IssueVoucher | 400 검증 / 409 중복(idem) |
| `POST /vouchers/{id}/transfer` | TransferVoucher | 404 / 409 STALE / 422 제약위반 |
| `POST /vouchers/{id}/redeem` | RedeemVoucher | 404 / 422 상태·제약 |
| `GET /vouchers?ownerId=&status=` | VoucherView(페이징) | — |
| `GET /accounts/{memberId}/balance` | BalanceView | 404 |
| `GET /accounts/{memberId}/statement` | LedgerStatement(페이징) | — |
| (내부) `POST /accounts/{id}/holds` `.../debits` `.../refunds` | ledger 이체 | 409 잔액부족/STALE |

> 원장 이체 엔드포인트는 **내부(서비스간)** 전용 — 게이트웨이 비공개, order/사가만 호출.

## 5. 영속 모델 (정합성 우선 → jOOQ/JDBC 권장)
- `voucher`(id, issuer_id, owner_id, face_amount, currency, kind, expires_at, scope, status, version, created_at, updated_at).
- `ledger_account`(id, member_id UNIQUE, balance_posted, balance_held, currency, version, ...).
- `ledger_entry`(id, account_id, type, amount, op_id, ref_type, ref_id, created_at) + **UNIQUE(op_id)**(멱등) + INDEX(account_id).
- 잔액 필드는 **Entry 합과 항상 일치**(파생 캐시) — 이체 시 Entry 삽입 + Account 잔액 갱신을 **한 트랜잭션**에.
- 금액은 `Money`(정수 minor unit + currency) — 부동소수 금지. 스키마는 Flyway + `ddl-auto=validate`([260702.006] 원칙).

## 6. 도메인 이벤트 계약 (payload)
`type` 규약 `"<Context>.<Aggregate><PastVerb>"`, 봉투는 common-platform `DomainEvent<T>`.

| type | payload(핵심) |
|---|---|
| `Voucher.VoucherIssued` | voucherId, issuerId, ownerId, faceValue, kind, constraints |
| `Voucher.VoucherTransferred` | voucherId, fromOwnerId, toOwnerId |
| `Voucher.VoucherRedeemed` | voucherId, ownerId, orderRef |
| `Voucher.VoucherExpired/Revoked` | voucherId, reason |
| `Ledger.FundsCredited/Held/Debited/Refunded` | accountId, amount, opId, ref |

> 하위호환: payload 필드 추가만. 삭제/의미변경은 `.v2` 신규 type. 소비자는 미지 필드 무시.

## 7. 테스트 시나리오 (회귀 가드 — DoD §11)
- **불변식(도메인 단위)**: 만료 바우처 상환 → 422; COUPON scope 위반 → 422; HOLD > available → 거부; 홀드 없는 DEBIT → 거부.
- **멱등**: 같은 `opId` 로 CreditFunds 2회 → 잔액 1회만 증가; 같은 `Idempotency-Key` 발행 2회 → 1건.
- **동시성**: 동일 계정 병렬 HOLD 2건(합계>잔액) → 하나만 성공(낙관락/유니크).
- **사가**: 발행→credit 반영; 주문 hold→debit→redeem; 실패 시 refund 보상으로 잔액 원복.
- **최종일관성**: VoucherIssued 후 BalanceView 가 (짧은 지연 뒤) credit 반영.

## 8. common-platform 매핑 & 착수 순서
- 소비: `starter-web` + `common-platform-bom`, 응답/에러/페이징/i18n/멱등/보안위임/이벤트코어.
- 도메인 에러: `VoucherErrorCode`/`LedgerErrorCode`(ErrorCode 구현 enum) + messages 번들.
- 패키지: 전략문서 §9 헥사고날(domain 순수, infrastructure 에 jOOQ/outbox/ACL).
- **착수 순서**: (1) ledger 계정·이체·멱등(잔액 진실) → (2) voucher 발행·상태 + `VoucherIssued→credit` 정책 → (3) transfer/redeem + 낙관락 → (4) 아웃박스·이벤트 발행 → (5) 회귀 가드.

# GM-20261007-004 — common-platform 0.2.8 업무 결과 기록

## 소비 계약

공통 logging 패키지의 `ActionRecord`는 `(String action, Outcome outcome, String errorCode, String requestId, String operationId, String actorId, List<String> relatedMemberIds, String traceId)` immutable record다. `Outcome`은 SUCCESS/FAILURE뿐이다. SUCCESS 오류 코드는 null, FAILURE는 owner 고정 오류 코드이며 회원 목록은 null 대신 `[]`다. action/errorCode는 고정 코드, ID는 opaque 식별자만 받는다. owner가 검증한 memberId를 직접 공급하며 auth subject를 자동 변환하지 않는다. 개인정보·예외 message·인자/응답 전체를 받는 API는 없다.

`RequestIds.current()`는 `AccessLogFilter`가 HTTP pair에 사용하는 동일 UUID다. HTTP 요청 attribute는 `RequestIds.HTTP_ATTRIBUTE`이며 UUID를 다시 발급하지 않는다. 기존 `TraceContextPropagation`/TaskDecorator는 이 값을 함께 전파한다. `ActionRecord.capture(action, outcome, errorCode, operationId, actorId, relatedMemberIds)`는 호출 시점 requestId/traceId를 snapshot한다. batch는 record 생성자 또는 `bind(requestId, traceId)`로 실제 원 요청 ID 또는 invocation ID를 명시하고, 원 요청 여부를 추정하지 않는다.

자동구성 `ActionLogger` bean을 주입받는다. no-TX는 실제 결과 확인 후 `record(record)`로 즉시 기록한다. TX는 **업무 owner의 최외곽 TX에 진입한 즉시** `var completion = actionLogger.bind()`를 호출하고, 업무 확인 후 `completion.record(record)`를 한 번 호출한다. binding 당시 실제 TX에 callback을 등록하고 correlation을 snapshot하므로 내부 REQUIRED/REQUIRES_NEW 코드와 async 결과에서도 외부 완료 시점/ID를 유지한다. `record(record)` 편의 메서드는 호출 당시 TX에만 결합하므로 owner 최외곽 경계에서만 쓴다.

```java
// @Transactional 업무 owner 메서드 내부, 내부 작업 전에 bind한다.
var completion = actionLogger.bind();
// ... owner 실제 업무 실행 및 결과 확인 ...
completion.record(ActionRecord.capture("member.signup", ActionRecord.Outcome.SUCCESS,
        null, operationId, verifiedMemberId, List.of()));
```

COMMITTED 후 owner SUCCESS/FAILURE를 그대로 기록한다. 실패 결과를 감사/ack와 함께 commit했어도 FAILURE다. ROLLED_BACK 후 owner FAILURE 코드를 보존하며, SUCCESS였으면 `TRANSACTION_ROLLED_BACK` FAILURE로 바꾼다. UNKNOWN 또는 actual-TX에 synchronization이 없으면 `mutuus.action_diagnostic` 진단만 남기며 확정 outcome은 없다. UNKNOWN 뒤 실제 결과를 확인하면 owner가 별도 확정 기록을 호출한다. callback 중복은 무시하고 BoundAction 결과를 두 번 공급하면 두 번째 결과를 무시하고 고정 진단을 남긴다(업무 예외를 발생시키지 않는다).

중단된 외부 TX나 savepoint 업무 의미를 추정하지 않는다. 최외곽 binding을 하지 않고 REQUIRES_NEW/NESTED 내부에서 binding하면 해당 현재 TX만 의미하며, 외부 업무 성공으로 사용하면 안 된다. NESTED rollback을 잡고 계속하는 owner는 최종 업무 결과를 FAILURE로 공급해야 한다. no-TX binding은 TX를 새로 시작/예약하지 않는다. 예외 때문에 결과 공급 없이 빠져나오면 owner의 외부 실패 경계가 고정 FAILURE를 공급해야 하며 라이브러리는 업무 결과를 만들지 않는다.

## 출력과 의존성

로거 `ai.mutuus.common.action`은 SLF4J key-value로 계약의 action/outcome/errorCode/requestId/operationId/actorId/relatedMemberIds와 `trace.id`, `event.dataset=mutuus.action`, `event.action`, `event.outcome=success|failure`, `error.code`, `operation.id`를 기록한다. 관련 회원은 실제 JSON 배열이다. `@timestamp`와 `service.name`은 기존 프로젝트 LogstashEncoder 및 service 설정이 담당한다. 기존 HTTP/job/user 필드는 변경하지 않는다.

기존 LogstashEncoder key-value provider는 null 값을 JSON에서 생략한다. 따라서 SUCCESS errorCode 및 미확인 actorId/operationId 등은 논리 값 null이며 기본 wire에서는 absent다. BO/소비자는 nullable 필드의 absent/null을 같은 미제공 값으로 처리하고, [] 관련 회원 배열은 생략하지 않는다. 별도 encoder나 nullable 값의 가짜 문자열은 만들지 않는다.

## 0.2.8 안전 경계

0.2.7 source `9a700d6`는 보존하고 새 버전으로 수정한다. metadata 캡처/생성자는 불신 값을 예외로 바꾸지 않고 제거한다. trace는 common 생성 형식인32 hex 또는 batch UUID만 허용하며 request UUID는 재발급/변경하지 않는다. 잘못된 opaque ID는 null, 관련 회원 목록의 잘못된 값은 제외하고 null 목록은 []로 만든다. owner action/outcome/errorCode 검증은 logger 내부에서 수행하고 잘못된 record는 확정 action 대신 고정 `ACTION_RECORD_INVALID` 진단만 남긴다.

# Secret Management Standard

This is the canonical secret-management standard for `common-platform` consumers.

**Status:** Accepted architecture; runtime implementation pending

**Canonical decision date:** 2026-08-27

**Scope:** Offline Secret Manager v2 encrypted values loaded by Spring Boot consumers

## Decision

- A valid `secret:v2:inline:` encrypted envelope is allowed in checked-in
  `application*.properties` or `application*.yml`. The encrypted envelope is not a
  reusable plaintext credential and its visibility alone is not a security finding.
- Plaintext passwords, private keys, PKCS#12 passwords, decrypted values, service
  tokens, and Nexus/admin credentials remain prohibited in the repository.
- Offline Secret Manager encrypts the plaintext with the target application's public
  key on a controlled workstation. The application decrypts it at startup with the
  corresponding private key.
- The encrypted value, private key, and private-key bootstrap password must be kept in
  separate control boundaries. They must never be committed or baked into one image
  as a recoverable set.
- `common-platform` owns an opt-in, fail-closed startup resolver in the existing
  `ai.mutuus.common:common-platform` JAR. Consumer services configure it; they do not
  copy cryptographic or Spring bootstrap code.
- The initial production scope is `spring.datasource.password` only. Additional
  target properties require a separate allowlist change and consumer verification.
- Runtime secret-manager SDK coupling, vault unseal, and automatic rotation remain
  outside the common JAR.

## Security Position

The checked-in encrypted envelope protects a secret at rest in source, artifacts,
configuration distribution, and backups. The actual security review boundaries are:

1. access control for the private key;
2. independent delivery of the PKCS#12 bootstrap password;
3. prevention of plaintext leakage through arguments, logs, exception messages,
   diagnostics, heap dumps, and temporary files;
4. protected review and release controls for changes to encrypted values; and
5. key separation and rotation by application and environment.

This design does not protect plaintext after the application host or JVM is fully
compromised. The application must hold the decrypted credential in memory long enough
to initialize its client.

AES-GCM authenticates the encrypted record and v2 AAD binds its metadata, but a public
key does not identify an authorized producer. Anyone who has the public key can create
a new cryptographically valid envelope. Protected branches, reviewed configuration
changes, signed build artifacts, and controlled deployment therefore establish
provenance. Cryptographic producer signatures are a future option, not part of v2.

## Canonical Property Contract

The canonical value is a complete Offline Secret Manager v2 JSON record encoded as
unpadded Base64URL and prefixed with `secret:v2:inline:`.

```properties
mutuus.common.secret.enabled=true
mutuus.common.secret.environment=stage
mutuus.common.secret.keystore=file:/run/mutuus/keys/golmok-backend-stage.p12
mutuus.common.secret.keystore-password-file=/run/secrets/golmok-key-password
spring.datasource.password=secret:v2:inline:<base64url-of-complete-v2-json>
```

Equivalent YAML is allowed. The keystore path and password-file path are locators,
not secret values. The files they identify must be mounted or granted independently
to the application identity. The bootstrap password content must not be placed in an
environment variable, JVM argument, system property, `.env`, application config, JAR,
or container image layer.

`secret:v2:file:` is not part of the first implementation. It may be added later as a
compatibility input, but it must resolve through the same validation pipeline and must
not become an automatic fallback from inline loading.

## Encrypted Record Contract

The decoded envelope must be a strict v2 record produced by Offline Secret Manager.
The resolver must validate all of the following before decrypting:

- `formatVersion == 2`;
- `algorithm == AES-256-GCM+RSA-OAEP-SHA256-MGF1-SHA256`;
- required fields exist exactly once and unknown or duplicate fields are rejected;
- Base64 fields, RSA encrypted-key length, 12-byte GCM nonce, and minimum GCM tag
  length are valid;
- record `program` equals `spring.application.name`;
- record `environment` equals the required
  `mutuus.common.secret.environment` value;
- record `configKey == database.password` for
  `spring.datasource.password`;
- `keyId` is allowed by the mounted keystore and rotation policy; and
- RSA-OAEP unwrap, AAD verification, and the GCM authentication tag all succeed.

The inline token has a hard maximum decoded size of 16 KiB. A blank decrypted result
is rejected.

## Common Module Responsibility

The implementation belongs in the existing `lib` module so web and batch consumers
can use the same behavior without adding another published Maven artifact.

```text
lib/src/main/java/ai/mutuus/common/secret/
├─ EncryptedSecretEnvironmentPostProcessor.java
├─ EncryptedSecretResolver.java
├─ EncryptedSecretRecord.java
├─ SecretBootstrapProperties.java
└─ SecretResolutionException.java

lib/src/main/resources/META-INF/spring.factories
└─ CommonEnvironmentPostProcessor, EncryptedSecretEnvironmentPostProcessor
```

The implementation uses JDK cryptography and Spring bootstrap APIs already available
to the common library. It must not add a Vault, KMS, or secret-manager client
dependency. Producer and consumer compatibility is locked with shared, non-secret
golden v2 test vectors rather than by invoking the desktop Secret Manager CLI as a
subprocess.

The resolver is inactive unless `mutuus.common.secret.enabled=true`. Existing
consumers therefore retain their current startup behavior until they opt in.

`common-platform` owns:

- the strict v2 decoder and RSA-OAEP/AES-GCM resolver;
- the opt-in Spring startup integration and fail-closed policy;
- the target-property/config-key allowlist;
- diagnostics that distinguish plaintext from accepted encrypted values; and
- sample, test, and canonical contract coverage.

`common-platform` does not own:

- Secret rotation or vault unseal workflows.
- Runtime secret-manager SDK coupling.
- Private-key issuance, custody, or deployment approval.

## Startup Contract

The dedicated `EnvironmentPostProcessor` runs after Spring Config Data has loaded and
before datasource, Flyway, and Hikari auto-configuration.

1. Locate supported encrypted target properties in individual property sources.
2. Reject an encrypted token combined with a higher-priority plaintext or differently
   sourced value for the same target; do not silently select one.
3. Read the explicit application name, secret environment, keystore locator, and
   bootstrap-password-file locator.
4. Read the bootstrap password as `char[]` from the independently protected file.
5. Decode, validate, and decrypt every configured target into temporary buffers.
6. Only after all targets succeed, add one highest-priority
   `mutuusDecryptedSecrets` property source.
7. Clear bootstrap-password arrays and unnecessary intermediate buffers in `finally`.
8. Log only the target property name, `keyId`, format version, and outcome.

All resolution is atomic: if one target fails, no decrypted property source is
installed and application startup fails.

The following conditions are fail-closed startup errors:

- opt-in is enabled but a token, environment, keystore, or bootstrap source is absent;
- plaintext and encrypted definitions conflict;
- malformed prefix or Base64 or JSON, oversize input, v1 input, or unknown algorithm;
- application, environment, config-key, or key-ID mismatch;
- inaccessible or invalid keystore/password file;
- RSA, GCM, or AAD validation failure; or
- blank decrypted output.

No fallback to plaintext, an existing environment variable, an alternate database,
or a previous encrypted value is permitted.

## `SecurityConfigAuditor` Contract

`SecurityConfigAuditor` remains diagnostic-only, but its classpath-secret rule must
distinguish plaintext from the canonical encrypted form:

- a nonblank secret-like property without the exact `secret:v2:inline:` prefix emits
  `security.config.secret_in_classpath_config`;
- a syntactically valid v2 inline token with the resolver enabled does not emit a
  plaintext-secret finding; and
- an inline-looking but malformed, unsupported, or unresolved token fails startup in
  the resolver and is never accepted merely because it has a prefix.

The auditor must never log the inline token or the decrypted value.

## Key and Bootstrap Boundary

- Generate a separate RSA key pair for each application and environment.
- Distribute only the public certificate to the controlled encryption workstation.
- Mount the encrypted PKCS#12 private key read-only and restrict it to the application
  service identity.
- Deliver the PKCS#12 password through a second mechanism such as systemd credentials,
  Docker or Kubernetes secret projection, or an OS credential store.
- Do not store the private key and bootstrap password in the same repository, config
  bundle, container image, or generally readable directory.
- During key rotation, allow only explicitly approved current and previous key IDs and
  remove the previous ID after all encrypted values have been reissued and verified.

## Options Considered

| Option | Decision | Reason |
|---|---|---|
| Plaintext external secret file | Legacy migration only | Removes values from Git but leaves plaintext on disk. |
| `secret:v2:file:` external JSON | Deferred compatibility | Strong separation, but adds file distribution and indirection that the selected properties-based operation does not need. |
| `secret:v2:inline:` in properties | **Accepted** | Keeps deployment simple while ciphertext remains safe without the separately controlled private key and bootstrap password. |
| Vault/KMS/HSM runtime integration | Future | Stronger key custody and rotation, but outside the current operating constraint and common JAR dependency boundary. |

## Implementation Plan and Gates

### Gate 0 - Policy and fixtures

- Update this canonical standard and consumer security guidance.
- Define non-secret golden v2 success, tamper, and wrong-metadata fixtures.
- Freeze the exact prefix, JSON fields, algorithm identifier, and size limit.

### Gate 1 - Offline Secret Manager producer

- Add `export-token` to emit `secret:v2:inline:` without emitting plaintext.
- Add a UI copy/export action that clears temporary buffers where practical.
- Keep real secret and PKCS#12 passwords out of CLI arguments.
- Verify token round trip, random nonce behavior, metadata binding, and output size.

### Gate 2 - common-platform resolver

- Implement the opt-in resolver inside `lib` and register its processor beside the
  existing `CommonEnvironmentPostProcessor`.
- Implement strict source-conflict detection, atomic property installation, safe
  errors, and buffer cleanup.
- Change `SecurityConfigAuditor` so accepted inline ciphertext is not reported as a
  plaintext classpath secret.

### Gate 3 - sample consumer proof

- Add an encrypted datasource-password example generated only from test credentials.
- Prove opt-out non-regression for both sample-api and sample-batch.
- Prove successful startup, failure cases, log non-disclosure, processor ordering,
  and actual datasource initialization in sample-api.
- Run the full reactor tests; static configuration inspection alone is not sufficient.

### Gate 4 - service adoption

- Upgrade one consumer to the approved common-platform version.
- Replace only `spring.datasource.password`; keep the approved URL, username,
  profile, and runtime mode unchanged.
- Remove competing plaintext password sources before enabling the resolver.
- Verify authenticated DB access, Flyway and Hikari startup, health, and a real API
  call without printing secret values.

No gate may be reported as complete from this document alone. Implementation, test,
and runtime evidence are separate requirements.

## Rotation and Rollback

Password rotation creates and reviews a new encrypted property token, updates the DB
credential in a coordinated window, restarts the application, and verifies real DB
and health checks. Old tokens remain encrypted but must be removed from active
configuration after the rollback window.

Rollback is a reviewed release or configuration rollback. The previous DB credential
and allowed key ID must remain valid until verification completes. There is no
automatic runtime fallback. Repository history and deployment authorization provide
rollback provenance; v2 encryption by itself does not prevent an authorized old token
from being replayed.

## Verification Checklist

- [ ] No plaintext password, private key, bootstrap password, or decrypted value is
      present in Git, JAR or image layers, arguments, logs, or temporary files.
- [ ] A checked-in canonical inline token does not trigger a plaintext-secret finding.
- [ ] A plaintext or malformed token does fail the required audit or startup path.
- [ ] Wrong program, environment, configKey, keyId, and all tamper cases fail startup.
- [ ] Mixed plaintext and encrypted property sources fail startup.
- [ ] Resolver opt-out leaves existing web and batch consumers unchanged.
- [ ] Resolver opt-in initializes the real target client before readiness succeeds.
- [ ] Private key and bootstrap password delivery are independently access-controlled.
- [ ] Rotation and reviewed rollback are proven without plaintext fallback.

## Superseded Runtime Contract

The earlier external plaintext `spring.config.import` workflow remains available only
as a migration bridge for consumers that have not adopted the encrypted resolver. It
is no longer the target standard and must not be used as an automatic fallback.
